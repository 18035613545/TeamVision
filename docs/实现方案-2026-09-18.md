## 2. 【L1】A3：splash 提前到重依赖之前

**现状**：`viewer.py:24-30` 顶层 import cv2/numpy/win32*/tkinter/PIL（onedir 冷启动时 cv2.pyd 86MB 是加载大头），splash 直到 `viewer.py:1361`（`__init__` 内 `tk.Tk()` 之后）才显示——双击到 splash 可见的间隔完全暴露给用户。`host.py` 同样问题（`host_ui.py` 依赖链）。

**改法（延迟 import，不拆模块）**：

1. `viewer.py:24-30` 删除顶层 `import cv2`、`import numpy as np`、`from PIL import Image, ImageTk`，改为模块内薄壳：
   ```python
   cv2 = np = Image = ImageTk = None
   def _load_heavy():
       global cv2, np, Image, ImageTk
       import cv2 as _cv2, numpy as _np
       from PIL import Image as _I, ImageTk as _IT
       cv2, np, Image, ImageTk = _cv2, _np, _I, _IT
   ```
   使用点全部是函数体内引用（A1 后上屏链 `viewer.py:2958-2961`、`2070-2072` 已是局部用法），无需改签名。
2. `main()`（`viewer.py:3300`）里、`ViewerApp` 构造之前先建一个**纯 tkinter 的最小 splash 窗**（tkinter 本身留在顶层，是 Tk 系最轻的依赖）；`root.update()` 让 splash 上屏后调 `_load_heavy()`，再进 `__init__`。
   - 现 `splash.show_splash(self.root)`（`viewer.py:1361`）改为接收外部 root 的"关闭 splash"时机点，`__init__` 不再创建窗口本身。
3. `host.py` 同构处理（它的重头也是 cv2/av；`av` 在 `codec.py` 内已是延迟导入，确认 `host` 顶层仅剩 cv2/numpy）。

**测试**：新增 `tests/test_startup_order.py`——用 `ast` 解析 `viewer.py`/`host.py` 顶层 import 列表，锁定"cv2/numpy/PIL 不出现在模块顶层"；`_load_heavy` 幂等。

**验收**：冷启动双击到 splash 可见 <0.5s（手机拍屏或 `Get-Process` 时间戳粗测即可）；全功能回归无新增失败；`python viewer.py` 源码模式正常。

**回退方案**：若某模块级引用漏网（如类属性默认值里用了 `np.`），报 `TypeError: 'NoneType'`——按栈改函数内引用即可，改动本身可单独 revert。

## 3. 【L1】A4：中继拷贝削减 + viewer 空闲退避

### 3.1 中继路径省一次整帧拷贝

**现状链**（成员上行帧转发给其他观看者）：`host.py:1179 _forward_upstream_frame` → `parse_video`（`common.py:245`）校验，其中 `common.py:285` `bytes(buf[5:5+length])` 做**拷贝 #1** → `host.py:1794/1805 _fwd_member_frame` 重新打包 `raw = _MSG_HDR.pack(kind, len(payload)) + payload` **拷贝 #2** → `route_frame`（`host.py:1682`）→ 各客户端队列共享同一 `raw`（无第三份）。09-17 方案说"2–3 次"，实为 2 次。

**改法**：`_forward_upstream_frame` 在**入口把整条原始消息（含 `_MSG_HDR` 那 5 字节头）物化为一段 bytes 一次**——这次物化本就是入队所必需的（当前它发生在 `common.py:285` 的 payload 切片上）；校验通过后把这段原始 bytes 直接交给 `_fwd_member_frame` 入队，`_fwd_member_frame`（`host.py:1805`）删除重新打包行——消息头字节序与长度字段原样有效，无需重建。即整帧物化次数 2→1。

**约束**：JPEG 分支（SOI 校验，`host.py:1202` 附近）与 `host.py:1187` 的 flags 校验逻辑不变；转发时**不得修改 payload 任何字节**（下游解码依赖原始 codec/flags 头）。

**测试**：新增 `tests/test_relay_zero_copy.py`——构造成员上行帧，断言中继出队得到的 bytes 与入队原始消息**逐字节相等**（现有 `tests/` 里已有中继 e2e 用例可扩断言）。CPU 收益 <0.1%，不单测性能，只锁正确性。

### 3.2 viewer poll 空闲退避

**现状**：`viewer.py:2851 def poll`、`viewer.py:2860` 固定 `after(15, …)`；无新帧时 `2873-2876` 提前返回但定时器仍 15ms 空转（约 0.3–0.8% 单核）。

**改法**：poll 内维护 `self._poll_idle_ms`（初始 15）：

- 收到新帧 → 重置 15；
- 连续无新帧 → 序列 15→33→50 封顶（每轮翻倍取序列值即可，不需要指数连续）；
- **不退避的旁路**：连接中/重连倒计时、状态叠加层需要刷新（`_update_status_overlay` 依赖的 RTT/状态变化）时保持 15ms——退避只针对"已连上且画面静止"场景。

**测试**：新增 `tests/test_viewer_poll_backoff.py`——桩 `root.after`，注入"有帧/无帧"序列，断言下一跳间隔按 15/33/50 变化、收帧即重置。

**验收**：静止画面对局外挂 10 分钟，任务管理器 viewer CPU 相对改前下降（本机粗测，不设硬指标）；收帧延迟无可感知回归（新帧到达后 ≤15ms 内被 poll 到——靠"有帧重置"保证）。

## 7. 【L2】C2：协议层单点

**现状**（全漂移修正后）：版本载体只有 `MAGIC_CLIENT=b"FS02"`（`common.py:39`）/`MAGIC_SERVER`（41），无 `PROTOCOL_VERSION`；action 字面量 host 17 处 / viewer 11 处（清单：`auth_result, req_keyframe, watch_reject, watch, unshare, register, login, probe, ping, pong, peers, cap, cap_probe`）；接收泵两份：`host.py:1527-1607 _client_recv_loop` 与 `viewer.py:357-540 Channel._receiver_loop`（同构：bytearray 累积 + `parse_message` 排空 + select 1s + 空闲判定）。

**方案**（纯重构、零行为变更，一次一子步各自全绿再进下一步）：

## 10. 【L2】D1：挑战-应答认证 + 协议 v2.2 源序号

**风险现状**：口令明文过网——`viewer.py:756` `send_msg(sock, {"action": action, "user": user, "pass": password})`（在 `_authenticate` `viewer.py:725`），host 校验在 `host.py:1339-1345`。存储侧已是 pbkdf2（`host.py:107-111`），**问题只在传输**。

### 10.1 认证设计（SRP 简化版，不引入第三方库）

```
登录:  C→S {action:login, user}
       S→C {action:chal, nonce(16B random), iter}
       C→S {action:auth_proof, user, proof=HMAC-SHA256(K, nonce)}
注册:  C→S {action:register, user}  →  S→C {action:chal, nonce}
       C→S {action:reg_proof, user, salt, dk, proof=HMAC(dk, nonce)}
       S 存 {salt, dk(=pbkdf2(pw,salt,iter)), iter}，验证 proof 后建号
```
- `K = accounts 里存的 dk`（注册时由观看端现算 pbkdf2 上送，host 存 salt+dk，**口令仍绝不留存明文**）；
- nonce 一次性、绑定连接、60s 过期；防重放即"同一 nonce 二次提交拒绝"；
- 中间人角度：能看到的只有 nonce 与 proof，proof 不可逆推 K；
- host 侧改造点：认证状态机 `host.py:1300ff`（现 `_register_allowed` 1258、校验 1339-1345）加 `awaiting_nonce` 态。

### 10.2 兼容窗口

`auth.chal_response: "require" | "allow_legacy"`，**默认 `require`**（默认安全是新基线）；`allow_legacy` 时旧客户端可走 `viewer.py:756` 的直发路径，host 写 WARNING（含用户名与来源地址）。旧客户端收到 `chal` 认不出来 → 明确拒绝文案「观看端版本过旧，请更新后重试」（依赖 §7 第 3 步的版本字段先落地，故 **C2 → D1 强制排序**）。一个发布周期后删 legacy 分支。

### 10.3 协议 v2.2 源序号（切源窗口丢旧帧）

现象：MultiView 切画面源窗口内，viewer 标签已更新但画面仍是旧源帧（"新标签 + 旧画面"）。
设计：转发/广播的帧 payload 前置 4B 单调 `source_seq`（每个源端启动时 `secrets.randbelow` 取起点，防跨会话混淆）；viewer 在 `_handle_ctrl` 收到源切换事件后，丢弃 `source_seq` 不属于新源的帧直到连续 3 帧一致。
**实现坑（09-17 方案未提）**：`_FRAME_HDR=">BIQ"`/`_VIDEO_HDR=">BIQBB"`（`common.py:216-218`）是定长 struct，加字段即改协议尺寸——必须走版本号分支（FS03 或握手协商），不能原地加；JPEG 路径 `viewer.py:494` 的手工 `unpack(">Q", payload[:8])` 同步改。
**开工前需真机复现一次**确认切源竞态仍存在（热键切源在 DPI 152% 机器上有静默切频道的史前科，见测试环境备注）。

**测试**：认证状态机单测（challenge 过期/重放/错 proof）、legacy 两模式 e2e、抓包断言 wire 上无口令子串；源序号：注入乱序帧断言丢弃计数。
