## 重点条目详述

### capture-002｜严重｜采集自愈链在生产中不可达（screen.py + pipeline.py）

```python
# screen.py:242-244  CaptureManager.grab 整个函数体在 try 内
except Exception as e:
    log.warning("采集错误: %s", e)
return None
```
`CaptureSource.grab`（pipeline.py:352-359）的 `_errors` 计数只在**异常上抛**时增加，而真实 `CaptureManager.grab` 把所有异常吞成 `None` → `_errors` 恒 0，`rebuild_on_errors=5` 的"重建采集器"恢复逻辑是死代码。空帧路径的兜底也被挡死：`_none_rebuild_requires_dead and self.working()`（pipeline.py:330-332）中 `working()` 只看句柄对象是否存在（screen.py:216-218），句柄活着但每帧抛错时恒 True → 永不重建。

- **回归假绿**：`tests/test_optimize_stage2.py:261-276` 用"会抛异常的 _FakeCap"验证这条路径——测试通过，生产失效。
- **触发**：RDP 断连/锁屏唤醒/GPU 重置/分辨率变化后 mss BitBlt 抛错、dxcam COMError → **对方永久看不到画面**，本端浑然不觉；告警以每帧一条（最高 ~100/秒）刷爆 5MB 滚动日志，约 1 分钟冲掉真实病因。
- **修复**：`CaptureManager.grab` 收缩 try 或改为累计 `_consecutive_errors` 并使 `working()` 反映之；告警加冷却；测试改用真实 `CaptureManager` 注入故障。

### net-015｜高｜第 103 条防滴字节超时可被绕过（common.py 泵 + host.py 回调）

泵每轮排空后**无条件** `on_buf("post", buf, now)`（common.py:481-482），不告知本轮是否消费掉完整消息；host 回调里 `else: partial_since = now`（host.py:1848）→ 半截消息每来一段字节就把 15s 计时起点后移。叠加 `on_rx` 每字节刷新 `last_rx_at`（60s 半开检测同样失效），且 `on_idle` 只在 select 空转 1 秒后才评估。攻击者发 `0x02 + length=32MB-1` 头后每 <15s 滴 1 字节，即可**无限期**占用接收线程 + fd + 连接名额 + ≤32MB 缓冲；`max_clients=32` 全占即对所有观众关门。
`git show 5b7ec7d^:host.py` 比对确认与重构前逻辑一致——属**第 103 条修复不彻底**，非回退。现有测试只覆盖"发 2 字节后彻底静默"，恰好绕开本洞。
**修复**：泵把"本轮消费的消息条数"传给 `on_buf`（或新增 `on_consume`），仅真正消费完整条消息才重置 `partial_since`；`note_rx()` 改为按完整消息刷新。

### auth-002｜高｜挑战-应答把密码学强度外包给了对端（common.py:100-113 + viewer.py:888-905）

观看端 `iter_ = int(chal.get("iter") or PBKDF2_ITERATIONS)` 后**原样传入** `derive_dk`，无任何区间校验；`nonce` 可为空串（`b64d("")==b""` → proof 退化为常量 `HMAC(dk,"")`，可永久重放）；`salt` 长度/内容无约束。链路上无 TLS、无响应签名：中间人回 `{iter:1, salt:自选}` 即得"一次迭代、攻击者选盐"的离线口令爆破 oracle（快 ~10⁵ 倍）；回 `{iter:10^9}` 则观看端接收线程在 PBKDF2 上挂死，重连即再挂。
**修复**：`derive_dk` 内钳制 `1000 ≤ iterations ≤ 2_000_000`、salt 限 32 位 hex；viewer 见 `iter != PBKDF2_ITERATIONS` 即判服务端异常拒登；proof 输入绑定 `nonce + user + 域分隔串`；根治需信道层（TLS/签名）——登记为与 auth-003/004 同族。

### ui-002｜高｜断线定格：第 102 条（B9）症状换路径复发（viewer.py）

poll 判定"有无变化"只看 `frame_serial`，而 serial 仅在 `_store_frame:1021` 与 `switch_source:1158` 递增；`_receiver_loop` 的四处状态跳变与 `finally` 收尾**既不 bump serial 也不清 `last_frame`** → 断线后 early-return 或重画旧帧，3044-3051 的"已断开，正在重连…"分支在曾出过一帧后永不可达。用户面对一张静止队友画面数分钟至数小时。同理第 12 条（fps 锁存）在"泵退出"路径上失效。

### net-016｜高｜一个劣质订阅者钉死全机画质（host.py ABR）
