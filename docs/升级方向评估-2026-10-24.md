# 升级方向评估（2026-10-24，v1.6.0 之后）

> 这份文档是"接下来做什么"的盘点，**不是方案**——每条都写清了它的证据、代价与
> 建议的取舍，供下一轮选题用。已有的落地记录在 `docs/audit/` 与 `docs/changelog.md`。
>
> 盘点方式：读当前代码 + 读 `docs/audit/` 里登记的未决项 + 对关键路径做**实测**
> （不是靠读代码猜）。每条都标了"是实测出来的还是读出来的"。

---

## 0. 先说结论

**最该做的不是新功能，是把 1.6.0 发出去。** 1.6.0 的代码在 main 上、CI 全绿，
但**没打 tag、没建 release、本机没跑过打包链**——用户拿不到。

发版之后的三条候选，按"性价比"排：

| 排序 | 方向 | 一句话 | 代价 | 风险 |
|---|---|---|---|---|
| 1 | **按订阅者差异化调档** | 慢的那位单独降画质，快的照旧 | 大（动 `route_frame` 与 `ClientInfo`） | 中 |
| 2 | **端到端加密** | 画面不再明文过网 | 中（加 `cryptography` 依赖） | 中 |
| 3 | **卸载清单纳入单测** | 改坏卸载清单从"打包时炸"变成"跑测试时炸" | 小 | 低 |

外加两条"不做会一直烂着"的：

| 排序 | 方向 | 一句话 | 代价 |
|---|---|---|---|
| A | **net-049 收口**（协议重新协商） | 共享端换版本后观看端不重新协商 | 中 |
| B | **装出来的东西能用**（CI 验启动 + 卸载清单核验） | 安装包"能编出来"但没人验"能用" | 小 |

## 2. 候选方向详述

### 2.1 net-049：协议次版本不重新协商（**实测确认是真问题**）

**现象**：`self._chal_capable` 是**跨连接持久缓存**。一旦置位，后续重连走
挑战-应答分支，**不再读回包里的 `proto`**——于是 `_expect_seq` 与 `_host_minor`
永远停在第一次探测时的值。

**后果**：观看端连的共享端**换了版本**（或换了地址、后面换了机器）之后，
观看端仍按旧的次版本解帧。net-048 修好后这个后果已降级为"序号遥测字段不更新"
（不再花屏），**但它是个静默失同步**。

**为什么一直没修**（net-049 原文记的）：修它要让 host 的 **8 个 `AUTH_RESULT`
发送点统一带 `proto`**，且必须保证**失败回包也带**——否则会把 `_chal_capable`
误刷成 False，从而**永久拒绝明文口令**（比现状更糟）。

**现在做的成本比当初低**：v1.6.0 刚把 `parse_feedback` / `feedback_is_decode_bound`
这类"协议层单一真源"的模式立起来（`common.FEEDBACK_FIELDS` 是同一份定义两端共用）。
把 `proto` 的发送收成一个 `_auth_result(sock, ok, text)` 辅助函数（**一个出口、
必然带 proto**），8 个 `send_msg(sock, {"action": Act.AUTH_RESULT, ...})` 点改成
调它——这比当初"在 8 处各加一个字段"可靠得多（**8 处实测：3 处形状完全一致**，
另 5 处是 `_reject_and_close` 里的变体，同样能收）。

**但要注意**：失败回包也带 proto 之后，观看端会**每次重连都重新协商**。这会
让 `_chal_capable` 每次连接都被刷一遍——正确，但要确认"旧服务端（无 proto 字段）"
那侧的行为不变（`_apply_probe_proto` 对"字段缺失"判 `present=False`，走既有口径），
以及**服务端拒绝旧观看端的那条文案路径**（net-047）不被这次改动误伤。

**成本**：改 host 的 8 个发送点 + viewer 的重协商逻辑 + 用例。中。
**收益**：消除一类静默失同步。**中高**。

### 2.2 net-045/050：帧序号的"选择性恢复"（**有坑，不建议单独做**）

net-045 承诺"把'整批重置'降级为'丢弃到下一个可解码点'"，至今没实现。

**为什么难**：最小可解码点的判定需要知道"这一批帧里从哪一帧起参考链还完整"，
而批次已经进了 `_decode_video_batch` 的逐帧循环。要做就得把批次切成
"可解前缀 + 待丢弃后缀"并让解码器状态与之对齐——涉及 `_got_key`、`_resync`、
`needs_keyframe` 三处门控的交互。

**更麻烦的是**：net-051 刚做的积压检测（`_backlog_exceeded`）与它**功能重叠**——
积压检测已经在做"落后明显就重置解码器 + 只收关键帧"（追新模式），那是**更粗的
同一个动作**。所以 net-045 的"选择性恢复"和 v1.6.0 的"追新模式"是两条并行的
恢复路径。

**建议**：**先别单独做**。等 1.7.0 做按订阅者差异化时一起设计——那时"丢哪些帧"
要按订阅者的解码能力决定，两件事本来就在一条链路上。

**成本**：单独做 = 高。**建议：推迟**。

### 2.3 按订阅者差异化调档（**价值最大，成本最高**）

**问题**：v1.6.0 的降档是**全局**的。慢观众的降档诉求会牵连快观众——为了
迁就一个用 4G 手机看的队友，所有人一起降码率。

**根因**：`route_frame` 的零重打包优化（同一份 bytes 广播给所有订阅者）
是**单编码器架构**的必然结果。要按订阅者差异化，得：

1. 认证期把对端次版本存进 `ClientInfo`（net-049 的副产品，正好一起做）
2. `route_frame` 按订阅者能力分桶打包（**零重打包优化失效**，慢的那位要单独
   `pack_video` + 单独编码）
3. 真正的解法是**多编码器**——为不同档位各养一个编码器（硬件编码器 93–110ms
   的构造代价，N 个档位 = N 倍构造）

**成本**：高。**收益**：高（这是"一个慢观众毁掉所有人体验"的唯一解）。
**建议**：1.7.0 的主线，但**先做 §2.1**（它是它的前置）。

### 2.4 端到端加密（**安全上该做，但不解决部署门槛**）

**现状**：画面是**明文 TCP**（README 与 install.md 都写明了）。1.4.0 起口令走
挑战-应答不再过网，但画面本身不加密。

**好消息**：共享密钥**已经存在**——`accounts.json` 的 `hash` 字段就是 pbkdf2
派生的 dk，观看端也能从口令派生同一个 dk（auth-002 的 proof 就这么算的）。
将来用 HKDF 从 dk 派生一个会话密钥就能加密，**零新增配置**。

**成本**：`requirements.txt` 加 `cryptography`（本仓库目前是"纯需求钉死"的风格，
加一条要写清上下界理由）；两端的加解密路径；密钥协商（用现有的 chal/proof
流程捎带即可）。

**但要说清楚它解决什么、不解决什么**：
- 解决：隧道/VPN 被监听时画面内容泄露
- **不解决**：部署门槛——加密了还是得自己搞 frp 隧道

**成本**：中。**收益**：安全上明显。**建议**：排在差异化调档之后。

### 2.5 CI 的两处盲区（**低风险高回报**）

**盲区一：安装包内容无人核验**。`package` job 验的是"能编出来"，不是"编出来
的东西对"——第 9 轮我往 `installer.iss` 写进一条 Inno **不存在**的指令，
单测与 lint 全绿，直到真编译才炸。现在有了一道"能编出来"的门，但：

- `installer.iss` 的**卸载清单**（哪些文件被删）无人核验
- `build_installer.bat` 的**产物守卫**（缺 `frpc.exe` 时是否报错）无人核验
- 装出来的程序**能不能正常启动**无人核验

**能做的**：在 `package` job 里加一步"装到临时目录 → 跑一次 `fps-host.exe --console`
→ 确认进程起来并写出 config.json"。这是**真端到端**的验证，成本低（Windows runner
上装一个 exe 而已）。

**盲区二：e2e 脚本进不了 CI（但原因不是"没写"）**。`e2e_multiview.py` /
`e2e_signalwin.py` / `soak_viewer_8h.py` / `stress_max_clients.py` 四个脚本
**本质是单机手动 GUI 验收工具**——它驱动**真实物理鼠标**（`SetCursorPos` +
`mouse_event`）、依赖本机显示布局假设（右侧无遮挡条带、面板同位放在右侧）、
用 `ImageGrab` 采样悬浮窗区域。**GitHub 的 Windows runner 没有交互桌面**，
这些脚本在那里跑不起来（连截图都拿不到）。

所以"把 e2e 进 CI"这句话是**错的**。多源互看其实**已经有单测覆盖**：
`tests/test_multiview.py`（359 行：订阅路由 / 关键帧门控 / roster / 成员转发）与
`tests/test_multiview_integration.py`（378 行：hub + 成员的集成路径）。

**真正缺的不是"多源互看"的覆盖，而是"装出来的东西能用"的验证**——即 §2.5 的
盲区一。e2e 脚本该保留的是**人工验收**的定位（它自己的注释就写明"并非 CI 用例"），
不该为了"进 CI"去改造成 headless 自动化——那是一笔与收益不成比例的投入。

**能做的**（按性价比）：
1. `package` job 里加一步"装到临时目录 → 跑 `fps-host.exe --console` → 确认进程
   起来并写出 config.json"——这是**真端到端**的验证，成本低。
2. `installer.iss` 的**卸载清单**纳入单测（哪些文件被删、哪些必须保留）——
   第 9 轮就是在这条上出的问题（我写了一条 Inno 不存在的指令）。
3. `build_installer.bat` 的产物守卫与 `installer.iss` 的口径对齐。

**成本**：小到中。**收益**：把"最脆的部分"从"手工验过"变成"每次 CI 都验"。

### 2.6 打包/安装器的剩余缺口（**比想象的小**）

先说清楚现状，免得高估：

- `build_installer.bat` 的守卫**已经很扎实**：从 `installer.iss` 现读
  `OutputBaseFilename`（不手抄）、产物存在性、≥1MiB 空壳检查、90MiB 硬下限
  （防 `_internal` 缺 DLL）、111MiB ±10% 目标带告警、陈旧包清理、签名失败即
  `exit 1`——**第 9 轮我就是在"守卫"这件事上出的问题，而守卫本身是好的**
  （出问题的是 `installer.iss` 里我自己写错的一条指令，守卫查不出来）。
- `sign_exe.ps1` 本身也细致：待签文件不存在即失败（不是"跳过"）、自签才放行
  `UnknownError`、CA 证书不放行、签名后复核哈希、临时名带 PID。

**真正的剩余缺口只有一条**：`installer.iss` 的**卸载清单**（哪些文件被删、
哪些必须保留）**没有单测**。第 9 轮我往 `[UninstallDelete]` 加了一条
**Inno 不存在的指令**（`UninstallablePathsDataFiles`），单测与 lint 全绿——
因为现有的单测只比对**版本号三处**，不查卸载清单。

**能做的**（小）：
1. `installer.iss` 的卸载清单纳入单测：断言 `%LOCALAPPDATA%\TeamVision`
   **不得**出现在卸载清单里（第 9 轮已经改对了，但**没有测试钉住**）、
   `{app}\fps-host` / `{app}\fps-viewer` 的数据文件**在**清单里、
   清单里**不得**出现 Inno 不存在的指令（已有一条反着钉的用例）。
2. `sign_exe.ps1` 在**受限 PowerShell 会话**下的健壮性——上一轮签名步骤失败过
   两次（终端会话缺 `Cert:` 驱动器 / `ConvertTo-SecureString` 模块自动加载
   失败），两次都靠临时脚本绕过去。**本机重测这两个 cmdlet 现在都可用**，
   所以那两次更可能是特定终端会话的环境问题，不是脚本缺陷——但脚本没做
   兜底，下次换个环境还会再遇到。

**成本**：小。**收益**：把"改坏卸载清单"从"打包时炸"提前到"跑测试时炸"。

## 3. 我建议的排序与理由

```
1. 发 v1.6.0                       ← 零新代码，用户收益最大
2. net-049 收口（协议重新协商）      ← 消除静默失同步，且是 §2.3 的前置
3. 卸载清单纳入单测 + CI 验"装出来能用"  ← 第 9 轮就是在卸载清单上出的问题
4. 1.7.0：按订阅者差异化调档        ← 价值最高的一轮
5. 端到端加密                       ← 安全
```

**理由**：

- 第 1 条不是"新工作"，是"把已经做完的事交付出去"。1.6.0 的质量反馈闭环对
  **已经有 1.5.0 的用户**是实打实的改善，而他们现在还拿不到。
- 第 2 条是"半做"里最该收的：它是一条**已登记的静默失同步**，且顺带把
  `ClientInfo` 的能力记录补上——那是第 4 条的前置。
- 第 3 条是**低风险高回报**：不改协议、不改行为，只是把"卸载清单改坏了"从
  "打包时炸"提前到"跑测试时炸"，并给"装出来的东西能用"加一道门。

## 4. 仍然不建议做的

| 事项 | 理由 |
|---|---|
| 房间号 / 自带打洞 | 要么自建 rendezvous/中继服务器（长期运维），要么 UDP 打洞 + TURN 兜底（成功率不是 100%，兜底又回到中继）。对朋友小队是过度工程。 |
| 拆包发版（两端分别出包） | `check_release` 已备好，但拆包要改 `installer.iss`、发布流程、签名清单。**用户并不需要**——装一个包更省事。 |
| 开 `--check-untyped-defs` | 会引入大量新错误（143 个 `def` 一个返回注解都没有），属独立议题。 |
| 给 5 个核心模块补返回注解 | 143 个 `def`，工作量与收益不成比例（mypy 现在查的是模块级语句与少量注解位置）。 |

2. **1.7.0 的主线选哪个**——按订阅者差异化调档（价值高、风险中）还是端到端
