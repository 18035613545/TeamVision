## 三、采集、编解码与转发时序

### capture-005｜低｜`--console` 不声明 DPI 感知，与 dxcam 的物理像素口径混用（仅首会话，且本机不可复现）

`host.py:3591` 只在 `not args.console` 时调用 `enable_dpi_awareness()`，命令行模式不主动声明。而 `screen.py` 的 `_dxgi_region()`（**243-263**，初稿误写 265-277；该处实为 `_monitor_rect()`）与 `_pick_output_idx()`（def 在 **279**）以 `_monitor_rect()`（mss = `EnumDisplayMonitors`）为基准做"虚拟桌面绝对坐标 → 显示器内相对坐标"的换算与越界判定，而 dxcam 的 `region` / `DesktopCoordinates` 是**物理**像素（`vendor/dxcam/core/output.py:41-45`、`dxcam.py:782-787`）。两者口径不同的前提是**进程未 DPI 感知且系统缩放 ≠100%**。

**两条必须收窄的前提（初稿均过头，已实测更正）**：

1. **"本机 152%"这一实测前提不成立**。本机实测：`shcore.SetProcessDpiAwareness(2)` 返回 0、`GetDpiForMonitor(MDT_EFFECTIVE_DPI) = 96`，mss 在感知与不感知两种状态下枚举到的都是 `2560x1440` —— 即**缩放 100%**。因此"只截到左上角约 1/scale² 面积""全等比较必然不相等"在本机不可复现，只能作为"外接开启缩放的屏幕"的用户会遇到的推论。ui-031 中同源的"152% DPI 放大"表述同此更正。
2. **漏了一条自愈路径**：`import dxcam` 本身就有副作用——`vendor/dxcam/__init__.py:188` 在模块级构造 `DXFactory()`，其 `core/output.py:20-24` 的 `Output.__post_init__` 会调 `shcore.SetProcessDpiAwareness(2)`。也就是说 `screen.py:183`（打包形态为 292）导入 dxcam 时进程**就地变成 per-monitor aware**，之后任何一次采集器重建（`CaptureSource._rebuild → _open → mss.MSS()`，169 行新建）枚举到的就是物理像素，混用随之消失。准确表述是"**仅第一个采集会话内口径错配，发生一次重建即自愈**"。

据此本条由"中"下调为"低"：需要 `--console` + 缩放≠100% + 区域采集或副屏 + 未发生重建，四者同时成立才可见；且修法上仍值得做——`enable_dpi_awareness()` 的声明不该与"是否有窗口"绑定（GUI 模式已由 ui-020 修对，命令行模式漏），或在未感知时整体退回 mss 后端，避免两套坐标混用。

### capture-006｜中｜`_pick_output_idx()` 在 vendor 路径接入之前就导入 dxcam

`screen.py:174` 调用 `_pick_output_idx()`，而把 `vendor/` 接入 `sys.path` 的 `ensure_vendor_on_path()` 要到 182 行才执行；**生产代码**里仅此一处调用（另有 `tests/test_bugfix_20260911.py:700` 一处测试直调，初稿"全仓仅此一处"不严谨）。于是 `_pick_output_idx` 内部的 `import dxcam` 抛 `ModuleNotFoundError`，被 314 行的 `except Exception → log.debug` 静默吞掉，直接 `return (0, self.monitor - 1)`。

前提已实测：运行环境 `fps-screen` 里 `importlib.util.find_spec('dxcam')` 为 **False**、裸 `import dxcam` 抛错（dxcam 只存在于 `vendor/`）。因此 capture-004 里**几何匹配那一半**（按显示器几何定位 `device_idx/output_idx`）在源码运行的第一个会话内等于不存在；同条修复中的"`monitor<=0` 回退 mss"（287-288）与 capture-003 的区域换算不依赖 dxcam，仍然生效——初稿"整套逻辑等于不存在"说得过满。由于 `ensure_vendor_on_path()` 改的是进程级 `sys.path`，一旦发生一次自愈重建再走 `_open()`，第二次匹配就能成功——在**多输出/多显卡**前提下表现为"同一份配置，故障恢复前后采到不同的显示器"（单屏机器两种口径都是 `(0,0)`，观察不到；本机即单屏）。打包 exe 不受影响（dxcam 在 `_MEIPASS` 可直接导入）。

修法：把 `ensure_vendor_on_path()` 提到 `_open()` 开头（或 `_pick_output_idx` 内部第一句），并把该 `except` 从 debug 提到"一次性 warning"。

### codec-010｜低｜`rate_control` 是从不传入的死参数，三处口径互相矛盾

`codec.py:71-72` 的 `VideoEncoder.__init__(..., rate_control="vbr")` 及 80、121-123 行的 cbr/vbr 分支实现完整（vbr 时 `maxrate = 1.5 × bitrate`），但**没有任何调用方传入该参数**：唯一构造点 `pipeline.py:131` 未带该形参，`host.py:3142`、`share.py:74` 都经 `pipeline.FrameEncoder` 走这条路；`DEFAULT_CONFIG["host"]["codec"]` 里也没有对应键（`grep '"rate_control"'` 仅命中 codec.py 自身）。也就是说它是"看起来可配、实际恒为 VBR"的死旋钮。

由此三处描述彼此冲突：`codec.py:9` 与 `:116` 称"默认 VBR，**可配 CBR**"（不可配）；`common.py:268` 把 `bitrate_kbps` 注释成"目标码率基线（**CBR**）"；`host.py:8` 的模块特性列表写"**CBR 码率**"。第 4 轮 item48 由 CBR 改 vbr 时只动了实现。

实际影响是排障口径：峰值码率可达名义值的 1.5 倍，而默认上行预算的假设是 `upstream_max_kbps = 2 × codec.bitrate_kbps`（第 107 条）——按"CBR"理解会算错上行占用；想切回 CBR 只能改代码。修法：要么补 `codec.rate_control` 配置键与面板项（真"可配"），要么删掉 cbr 分支并把三处注释统一为 VBR；不要停在中间态。

### codec-011｜低｜静止且编码器已弃时，关键帧请求永无响应

`share.py` 的 `force_idr` 有一条返回 `(None, None)` 后直接 `return False` 的路径，走不到函数末尾"重发缓存帧 / JPEG 兜底"的分支。**两处措辞更正**：①实际可达形态是 `pipeline.py:198` 的第二个判据 `not self._encoder.available`（编码器 permafailed，而 `_encode_send` 因 `grab()` 恒 None 不再被调用，于是永不被丢弃）；若真是 `self._encoder is None`，`last_is_video` 一般为 False，已经走 272 行的 JPEG 重发。②默认 `capture.backend="dxgi"` + 静止检测关闭时，画面静止期间 `grab()` 恒返回 None，正是该分支的常态。

后果：新接入的观众一直等不到 IDR，画面保持黑屏，直到共享端画面发生变化。此时 `ef.frame` 其实在手——注意它是**缩放后**的 BGR（初稿写"原始 BGR"有误，`host.py:3183` 注释亦称"缩放后帧"），完全可以交给 `_fe.encode(force_key=True)` 走 JPEG 回退。调用方按 codec-008 的约定保留了 `key_evt` 空转重试，所以不会误丢请求，只是永远等不到响应。

### codec-012｜低｜`set_fps` 先提交状态再构造，失败后该帧率档不再重试（初稿定中偏高）

`codec-002（2026-09-18）`：与 `set_bitrate` 同款"锁外构造、锁内切换"——旧实现在锁内 `_recreate(keep_old_on_failure=False)`，编码线程要停等一次 NVENC 拆装（约 100ms），且新上下文建不出来时连原本可用的旧编码器也一起拆掉（自毁后只能回退 JPEG，直到下次成功重建）。这个目标已达成；留的尾巴是失败路径：

```python
with self._lock:
    if self._closed or self._permafailed or fps == self._fps:
        return
    self._fps = fps          # ← 状态先提交
...
ctx, name = self._create_ctx_with(names, bitrate)
if ctx is None:
    return                   # ← 注释称"下次再试"，但同一 fps 已命中上面的提前返回
```

代码片段与 `codec.py:266-274` 逐字一致，274 行的"下次再试"注释确实与实现相反。`pipeline.py:112-115` 也不看返回值（`set_fps` 全仓唯一调用点就是 114），两侧各自记为"已生效"。

**但初稿的可达性与后果都被夸大，三处更正**：

1. **触发条件写错了**。初稿称"NVENC 并发会话上限可触发（GeForce 3~5 会话，本机 host + share 已占 2）"——`codec.py:178-190` 是**沿整条候选链试到底**，而 `_pick_encoder()` 里的 `av.Codec(name, "w")` 只查编码器名、不开会话，因此 nvenc 全部失败后仍会用 `libx265` / `libx264` 成功。实测本机：`hevc_nvenc` / `h264_nvenc` open 失败时 `libx265` / `libx264` open 均 **OK**。真实触发条件只剩"含软件编码器在内全部 open 失败"（驱动挂死、OOM 级别）。
2. **不是"每帧下发同一值反复撞门"**。`pipeline.py:113` 的 `fps != self._enc_fps` 守卫使 `set_fps` 只在值变化时调用一次，失败后 115 行仍记 `_enc_fps` → 两侧各只试一次，是"**双重挡住**"而非反复重试（结论相同，机制描述需更正）。
3. **错位不会"长期"存在**。`self._fps` 已提交，下一次任何 `_recreate`（`set_bitrate` 超出 ±15%、`_encode_locked:304-306` 尺寸变化、编码失败自愈）都会带着 `self._fps` 建 ctx（`codec.py:166-167`），错位随之静默消失；ABR 活跃期是秒级。

综合三点，按报告自身判据（须有可证实的可达路径）本条降为**低**。仍值得修的点是实质但轻微的：`set_fps` 应在失败时回滚 `self._fps` 或引入 `_pending_fps`，并返回是否生效供 `pipeline` 落账——否则"注释与实现相反 + 两侧状态各记一份"是下一次引真 bug 的温床。

### codec-013｜低｜静止期强制 IDR 的门禁只装在 share 侧

`pipeline.py:190-207` + `host.py:3091-3095`：`force_idr` 原样返回 `(nal, is_key, …)`，host 侧直接写 `slot["is_key"] = is_key` 并消费 `force_key`，既不校验 `is_key` 也不校验缓存帧尺寸。`share.py:263-265` 已加 `if not is_key: return False`（264 行注释自陈"codec-004 同款"；初稿误写 255-258，那是 `last_is_video` 与 `err` 分支），host 这侧缺同一道门。**另一处更正**：初稿暗示 share 侧还有"缓存帧尺寸"这道门——实际**两侧都没有**尺寸校验（`share.py:253-272`、`host.py:3061-3105` 均只判 `is_key`/None），尺寸不一致一律由 `codec.py:304-306` 的自动重建吸收。即 codec-004 修复中"校验缓存帧尺寸"那半边，**host 与 share 两边都没落地**。

《修复记录》第 4 节写的是"host.py、share.py"两处都改，实际只改了 share 侧。可达性上受 `perf.still.enabled=False` 限制，主要在采集停摆（capture-002 场景）时被反复走到，此时等关键帧的订阅者一直空等；帧流正常时下一个真帧会补上，故影响有限但口径确实漏了一处。

### codec-014｜中｜客户端 `req_keyframe` 无合并、无限速（初稿定低偏低）

`host.py:2066-2075` 的 `REQ_KEYFRAME` 分支无条件 `runtime.force_key = True; _wake_raw(runtime)`。net-020 的 `allow_ctrl_broadcast()` 配额只挂在 WATCH / UNSHARE 上，上行令牌桶只管 `MSG_VIDEO` / `MSG_FRAME`，控制消息整体没有配额。

对端发一条约 40 字节的消息即可把本机编码器钉成帧帧 IDR（每次 IDR 的码率开销远高于 P 帧）；`peer:N` 分支更糟——每条消息都走 `_sharer_sock`（2344 行，持 `clients_lock` 全表扫描）+ `_send_ctrl_safe` 同步 sendall，而同一动作的内部愈合路径 `_request_peer_keyframe`（2356 行）明明带 1 秒冷却，两端口径不一致。默认 `auth.enabled=True` 但 `allow_register="open"`，即公网观众可自建账号登录后触发。net-021 修的是"丢帧置 force_key"，客户端主动路径没纳管。

### net-029｜中｜超限的控制消息静默丢弃，绕过观看端自纠

`host.py:2050-2059` 对超限的 WATCH / UNSHARE 走 `if not info.allow_ctrl_broadcast(): return None`——既不改 `watch_source`，也**不回 `WATCH_REJECT`**。而 `viewer.py:1328-1366` 的 `switch_source` 是"先本地提交、再发包"，只有收到 `WATCH_REJECT` 才 `_revert_source` 或回落 local（803-816）。

于是被丢弃的那条会让标签显示"队友·X"而实际是本地画面；如果被丢的是"切回 local"那条，host 仍按已失效的 peer 源路由，结果是**永久黑屏且没有任何自愈路径**。触发面不窄：配额 burst=3/10s 且 WATCH 与 UNSHARE 共用同一桶，重连自动补发 WATCH（`viewer.py:449-451`）、队友离线自动切回 local（1517）、面板双击切源（2613）都能在 10 秒内叠到 4 条。这是 net-020 修复引入的新错误行为——加了配额，却没给被限流的请求一个回话。

修法：限流命中时回 `WATCH_REJECT`（复用现有文案分支），或干脆把配额做成"合并待处理"而非丢弃。

## 四、host 网络与并发

### net-027 / net-028｜中｜`parse_addr`：空主机未判（既有缺口）与裸 IPv6+端口被改坏（net-018 回归）

`common.py:684-732` 在 net-018 里被重写以支持 IPv6 字面量。两个方向各留一条问题，但**归因不同**（初稿把两条都算作 net-018 的账，经实测复刻旧实现后已更正）：

**net-027（空主机被放行——既有缺口，非本轮引入）**：函数对空串与纯空白抛 `ValueError`（正确），但 `":5700"` 这类"冒号前为空"的输入走单冒号分支，`host = ""` 被直接返回。观看端的地址校验器 `viewer.py:204 _canonical_addr()` 复用它做第 94 条校验，于是空主机被当作合法地址写进频道表。实测：`parse_addr(':5700') -> ('', 5700)`、`_canonical_addr(':5700') -> ('', 5700)`；**复刻 net-018 之前的旧实现得到同样的 `('', 5700)`**，所以这是第 94 条校验的口径缺口，不是 IPv6 改造带进来的。

后果的准确描述也要更正：观看端实际走 `viewer.py:395 socket.create_connection((host, port), timeout=10)`，`getaddrinfo('', 5700)` 会解析到本机链路 IPv6（`fe80::…`），实测表现为**每轮重连白等 10 秒后进入无限退避**；初稿写的 `WinError 10049` 是直接用 `socket.connect(('',5700))` 探针得到的结果，不是本程序真实路径的行为。

**net-028（回归，确系 net-018 引入）**：新增的"裸 IPv6"分支条件是 `addr_str.count(":") >= 2` 且**先于** rsplit 执行，于是 `::1:5700` 这种"裸 IPv6 + 端口"被整串当主机名——实测返回 `('::1:5700', 5700)`，而旧实现正确地返回 `('::1', 5700)`。也就是说为了支持 `[::1]:5700`（这一形现在确实对了），把另一种原本可用的写法改坏了；而 `::1` 恰是 A0 双栈回环监听下的合法常见目标（frpc 的 `localhost` 回连优先解析为 `::1`）。更隐蔽的是 Windows 下 `getaddrinfo('::1:5700', 5700)` 会把这串**曲解成 `::0.1.87.0`** 之类的地址而不是直接报错，比"连不上"更难查。

修法：`":5700"` 分支补 `if not host: raise ValueError("地址缺少主机")`；`count(":") >= 2` 分支先判断"末段是否为纯数字"，是则仍按 `host:port` 拆分，否则整串作主机名 + 默认端口。

### net-030｜高｜总时限只在 `select` 空转时评估，滴字节照旧可永久占用

`host.py:2123-2128` 的 `_on_idle` 是唯一检查 `partial_since`（单条消息总时限）与 `last_rx_at`（半开检测）的地方，而泵里它只在 `select` 空转满 1 秒时被调用：`r,_,_ = select([sock],[],[],1.0); if not r: on_idle(...)`。对端每 0.4~0.9 秒投 1 字节，`not r` 永不成立，`msg_timeout_s=15s` 与 `idle_s=60s` 两条判据一次都不会执行。

实测（对真实 `message_pump` 下 socketpair）：声明 `0x02 + len=32MB-1` 后每 0.4 秒滴 1 字节，12 秒内 `on_idle` 被调用 **0 次**、泵不退出；把间隔改为 1.5 秒则正常报"单条消息超时"。

需要说清的是：**net-015 的修复本身没写错**——`_on_buf`（`host.py:2130`）"仅在 `n_msgs > 0` 时重置 `partial_since` 并 `note_rx`"的记账是对的，探针也证实首字节起算、完整消息才重置。失效点在**评估时机**：只修了计时起点，没修评估点。认证阶段的绝对 deadline（1749-1753、net-022 的 1955）只覆盖 `_auth_*_phase`，不覆盖接收循环；准入关闭时 `_auth_optional_phase` 对静默旧客户端返回 `(True, None)`，故接收循环里这条洞未认证也能碰到。

**成立范围要收窄**（初稿的"永久占用"过宽）：发送侧 `_client_sender_loop` 自带 `sock.settimeout(2.0)`（`host.py:781/796`），sendall 失败即 `_drop_client("发送失败")`——所以"滴字节但不读下行"的对端会在约 2 秒内被拆掉。本条只对**仍持续把下行读干净的恶意对端**成立（这在协议上完全做得到：正常收帧但不发完整消息）。修法：`select` 的 timeout 取 `min(1.0, 剩余超时余量)`，或在每个 recv 分块之后评估一次两条判据。

### net-031｜中｜握手阶段没有总时限（但危害是速率型 DoS，≤40 秒自愈——初稿定高有误）

`host.py:1632-1637` 的 `_do_handshake` 只设 `sock.settimeout(HANDSHAKE_TIMEOUT_S)`（常量 = 10.0，`host.py:95`），随后 `server_handshake`（`common.py:676-681`）内部 `recv_exact(sock, 4)`（定义在 **`common.py:644-665`**，docstring 645-651）**不传 deadline**。"握手路径没有总时限、而同族认证路径有（net-022）"这个结论成立。

**但初稿把危害写重了，此处更正**：`recv_exact` 的 docstring 描述的攻击前提是"声称一个**超长** payload 后每 (timeout−1) 秒喂 1 字节"，而握手读的是**固定 4 字节**，且 `recv_exact`（654-665）并不吞 `socket.timeout`——超时直接冒泡。因此最坏情况是 `4 × 10s = 40 秒` 必然结束（要么凑满 4 字节进入 `_do_auth`，要么被 `_do_handshake` 捕获后关连接），名额随即在 `finally`（2225-2229）归还。实测（把 timeout 缩到 0.5s、每 0.4s 喂 1 字节）：喂满 `FS02` 用时 1.6s 返回成功；只喂 `FS0` 则 1.7s 抛 `TimeoutError`。

所以正确的定性是**速率型 DoS**：攻击者以"每约 5 秒新建一条连接并滴 1 字节"的速率持续拨号，就能把 `max_pending_auth = max(4, max_clients//4) = 8`（`host.py:1174`，默认 `max_clients=32`）长期占满，期间每个新观众在 2211-2212 行以"未认证连接数已达上限"被 close。区别于初稿的"永久占用、只能重启 host"：**攻击停止后 ≤40 秒自愈**，代价是攻击期间的持续服务拒绝。据此由"高"下调为"中"（仍需修：给握手传 deadline 与认证阶段同口径）。

### net-032｜高｜`delay` 缺 `nonlocal`，公网自检线程一启动即死

`host.py:2673-2692` 的 `_probe()` 里，循环第一句就读 `delay`：

```python
waited = 0.0
while not runtime.stop_event.is_set():
    host, pub_port = target
    if runtime.stop_event.wait(max(0.0, delay - waited)):   # 2679 读
        return
    waited = 0.0
    delay = 600.0                                           # 2682 写
```

Python 在编译期就因 2682 的赋值把 `delay` 定为 `_probe` 的局部名，没有 `nonlocal`，因此**首次迭代即 `UnboundLocalError`**。已用 `co_varnames=('waited','host','pub_port','delay',…)` / `co_freevars=('_probe_once','port','runtime','target')` 与同型最小复现双向证实。

可达性：只要配了 `frp.public_addr` 且 frpc 在运行，`_start_tunnel_selfcheck`（2667-2671）通过后即起 daemon 线程（2729），线程内异常无人接。后果是自检从"启动跑一次"退化为"从不跑"：`_net_status` 恒为 `unknown`，面板 `host_ui.py:881` 的 `_stale` 计算恒为 False（其"结论已过期"文案分支因此不可达；877 行是取 `net_status` 的那行），诊断报告里也没有隧道结论——第 5 轮 net-023 的三项改动全部成为死代码。`tests/` 里没有 `_start_tunnel_selfcheck` 的用例（只有 test_diag 的替身），所以 595 全绿没拦住它。

修法：`delay` 初值移到 `_probe` 开头或加 `nonlocal`；线程体外加 try/except 记日志；补一个真正起线程跑到第一次迭代的用例。

### net-033｜中｜自检循环不复核隧道是否仍在运行（net-032 的连带隐患）

`host.py:2670-2671` 的 `if not runtime.frp.is_running(): return` 只在 `_start_tunnel_selfcheck` 入口判一次，`_probe` 的 while 循环内不再复核；调用点唯一（`run_server`，2899），之后除 `stop_event` 外没有任何取消路径。

当前因为 net-032 线程根本跑不起来，这条**不成立**（这也是为什么不能按"隧道已停仍在外部连接"来定级）。但 net-032 一旦按最小改动修好，它立刻变成：用户在面板停掉 frpc，host 仍每 10 分钟向 `public_addr` 发起 DNS + TCP 外连直到进程退出，同时把面板结论改写成"失败"。两条必须一起改——**修 net-032 时若在循环内不加 `is_running()` 复核，就是把一个死代码换成一个外连隐患**。

## 五、接收与转发链（观看端侧）

### net-034｜高｜追新判据建立在两端墙钟差上，跨机时钟偏差直接变成黑屏

`viewer.py:680-682`：`lag_us = time.time_ns() // 1000 - int(batch[-1][0])`，而 `batch[-1][0]` 是**共享端墙钟**时间戳。两端之间没有任何时钟同步约束（全仓无偏移估计），只要共享端时钟比观看端**慢** ≥2.5 秒，`lag_us` 就恒大于 `_BACKLOG_LAG_US` → 每次 `recv` 轮都判定积压：`_resync=True` + `_decoder.reset()` + `_got_key=False`（685-693），随后 `_decode_video_batch:737` 丢弃全部 P 帧直到 IDR。`_resync_at` 的 10 秒冷却只是把现象变成"每 10 秒黑一次"，不会解除。触发点在接收泵每次 `recv(65536)` 之后（`viewer.py:526`），无需用户操作。

**ts 的真实来源链（初稿引错，已更正）**：视频路径的 ts 恒为**显式入参**，`common.py:389` 那条"缺省取本机时刻"的分支在视频路径上从不执行；源头是 `host.py:2988` 的 `ts_micros = int(time.time() * 1e6)`——即**采集时刻**（不是初稿说的"编码输出时刻"），经 `codec.py:314` 写入 `frame.pts`、`codec.py:350-353` 出 `out_ts`，主路径在 `host.py:3036` 打包（3094 是静止期强制 IDR 的支路）。这一更正不改变结论，只改变归因描述：偏差来源仍是"对端墙钟的采集时刻"。

**两处需要收窄的说法**：① 空窗不是固定 2 秒——685-693 同时发了 `_request_keyframe`，正常一个 RTT 内就会回 IDR，2 秒（`keyint=60`@30fps）是**无人响应时的上界**，应表述为"≤2 秒，多数远小于"。② "跨机时钟相差数秒是常见情况"这句**没有仓库内证据**（`logs/` 里"检测到解码积压"零命中），且要注意方向性：只有 host 慢于 viewer ≥2.5s 才误触发，host 快时 `lag_us` 为负、被 `0 <=` 排除。因此本条的准确定性是"**误触发的前提条件明确存在但发生率未证实**"，其危害机制（一旦满足即周期性黑屏且不自愈）成立。另注：追新丢弃期间 524-525 仍在刷新 `last_media_rx`，所以 480-482 的关键帧自救在该窗口内不会叠加触发；`_resync` 另有 1347（switch_source）一处退出。

修法：判据改用本端单调钟 + 到达间隔（例如"批次内相邻帧到达间隔显著小于帧标称间隔"即说明在追帧），或首次对齐估出偏移后再用 ts。

### net-035｜高｜真积压落在判据死区，net-017 的原症状未修

与 net-034 同一行的另一半：`lagged = 0 <= lag_us <= 10_000_000 and lag_us > 2_500_000`——延迟一旦真的超过 10 秒就被当"脏数据/时钟异常"排除，追新不触发。另一判据 `len(batch) >= _BACKLOG_BATCH_FRAMES(12)` 受单次 `recv(65536)` 上限制约（`common.py:509`），且 `_on_chunk`（496-499）每次 recv 前清空批次、**不跨 recv 累积**，于是等价于要求"64KB 装得下 12 帧 = 平均 ≤5.46KB/帧"；默认 2500kbps@30fps 约 10417 B/帧（`common.py:268`）→ 该档下只有约 6 帧，**判据不可达**。

**"恒为/永不"要收窄**（初稿过头）：结论只在默认档成立。ABR 可把码率降到 `min_bitrate_kbps=400`（`pipeline.py:498`、`host.py:3409-3416`）→ 约 38 帧/recv；帧率取 60（`host_ui.py:225` 的回退值）→ 约 15 帧 > 12；低运动场景 P 帧也远小于均值。所以准确表述是"**默认与常见配置下不可达，只在低码率或高帧率档才可能触发**"。同理 `viewer.py:284` 是 rcvbuf 的定义处，真正生效在 396 行的 `tune_socket`。

即便如此，本条的核心结论仍成立：延迟越过 10 秒上界后判据失效，而 4MB 接收缓冲约容 13 秒视频，解码慢于到达（4K/HEVC 软解）时延迟可越过该门槛，此时 `_on_idle` 只看 `last_rx`（积压期间字节持续到达）→ 也不重连。net-017 登记的原症状"延迟可爬升至秒级且永不回落"在**最严重的那一段区间内依然成立**；即该修复同时具备误触发（net-034）与漏触发（本条）两个方向。

### net-036｜中｜观看端没有接上"按完整消息刷新"

net-015 的按消息计数刷新只落在 host 侧：`viewer.py:541-545` 调 `message_pump` 时**不传 `on_buf`**，`_on_rx` 由泵在每个 recv 分块上调用（`common.py:518-519`），因此 `last_rx` 按字节刷新。叠加 net-030 的"只在空转时评估"，对端（含被劫持的隧道中转）每 5 秒内滴 1 字节即可让 `read_idle_s` 停滞判定永不成立，频道被钉在 `status="receiving"` + 画面定格，而 `last_media_rx` 的增长只会反复 `_request_keyframe`（480-482）自我强化。第 10 条的硬断线检测同时失效。与 ui-002 修掉的"定格"是同症状的另一条路径。

### ui-023｜中｜统计容器的跨线程竞态被误报成断线

ui-010 新增的 `_reset_stats_locked()`（`viewer.py:1346`，主线程 `switch_source` 持 `self.lock` 时 `seq.clear()`）与接收线程 `_store_frame` 对同样两个列表的裁剪竞争，而后者的裁剪写在 `self.lock` **之外**：`while self._fps_times and self._fps_times[0] <= cutoff: pop(0)`（1165-1166）、`if len(self._latency_samples) > 5: pop(0)`（1174-1175）。判空与 `pop` 之间被 clear → `IndexError: pop from empty list`，沿 `message_pump` 冒到 `_receiver_loop:546` 的 except，被判为断线并整条重连（画面闪断）。

**跨线程调用点要更正**（初稿三个里有两个错）：面板 2613 与热键 3679 其实都跑在 **Tk 主线程**上（`_post_ui` 只入队、由 poll 在主线程排空，见 1892-1910 / 3621-3629），与 `switch_source` 同线程，不构成竞态。真正的跨线程点是 **`viewer.py:813` 与 `1517`**——两者都在接收线程的 `_handle_ctrl` 里（1517 不是 Timer，初稿记错），与 `_store_frame` 分属两线程。竞态结论仍成立，但命中窗口也要更正："帧间隔 >1 秒最易命中"是反的——>1s 时那个 `while` 循环体根本不 pop；窗口大小随帧率上升，真实风险面是主线程在 1316-1347 持锁期间（含 1333-1335 的解码器重建，可能达数百毫秒）。修法：两处裁剪统一走 `*_locked` 版本并全程持 `self.lock`。

### ui-029｜低｜断线态下 poll 空闲退避永久失效

ui-002 之后 poll 的早退三元组包含 `_last_frame_serial`，但它只在 `_show_frame` 成功贴图时落账（3352），而 `_invalidate_media` 会额外再 bump 一次 serial（366）→ 纯文字分支的 serial 与落账值永不相等，早退条件恒不成立。结果：`_poll_idle_ms` 被 3249 钉在 15ms，A4 §3.2 设计的 15→33→50ms 空闲退避在"host 离线 / 正在重连"这一常态下不再生效，每 15ms 做两次 `_update_status_overlay` 加多次跨线程取锁。`_show_text` 自身有 `_last_text` 去重，所以是 CPU 白烧而非卡死；host 关机后长期挂机可观测。

## 六、认证与账户

### auth-014｜高｜账号存在性仍可用一条消息判定，且可离线批量

`host.py:1714-1721` 的 `_fake_login_salt(user) = hmac.new(b"tv-nouser", user, "sha256").hexdigest()[:32]`——密钥写死在源码里、无服务端随机量，账号不存在时该值被**原样放进 `CHAL.salt`**（1880），而真实账号下发的是 `secrets.token_hex(16)`。

对端（局域网或 frp 隧道）匿名发 `{login, user:"x", pass:""}`，收到 CHAL 后本地用同一个函数重算比对，即可 100% 判定账号是否存在；无需交互完成认证、可离线批量、无速度限制（服务端限速已按项目裁定不做）。

这与"待信道层根治"的 auth-004 不是一回事，成本也完全不是一个量级：把伪盐密钥改成启动时随机（`token_hex`，落盘在 accounts.json 同目录）、或对不存在的账号也下发真随机盐 + 做同代价比较，即可消除。当前 `tests/test_d1_challenge_auth.py:200-203` 只断言伪盐"形如 `^[0-9a-f]{32}$`"，没有断言"不可预测 / 不可与真盐区分"，正是漏网处（见 T-04 一节）。

### auth-015｜中｜升级安装删空账户，即静默重开自助注册窗口

`host.py:321-331` 的 `bootstrap_used()` 只看 `<accounts>.bootstrap-used` 标记文件是否存在（160-184 是 `_load()`，初稿在正文里把两者写串了；总览表的两个行号分别对应 `_load` 与 `bootstrap_used`，无误），而标记**只在 `register` / `register_derived` 成功后**写（369、496），`_load()` 读到非空账户表时不会回填。`_register_allowed`（1666-1670）的判据是 `count()==0 and not bootstrap_used()`。

于是所有在本轮之前生成的 `accounts.json` 都没有标记文件：升级到 a5b1598 后，只要把账户删空（团队解散、清理测试账号），bootstrap 策略下"第一个账户可自助注册"的窗口就重新打开。**须加限定**（初稿未加）：`allow_register` 默认值是 `"open"`（`common.py:290/345`），默认配置下注册本来就全开，所以"任意远端可自建账号看屏"这个后果只对**显式选了 bootstrap 策略的主机**成立。本条定中的理由随之改为"**已按建议加固过的配置，会在删空账户时静默退回加固前**"，而不是"默认即失守"。`host_ui.py:671` 的面板确认文案却明确承诺"窗口不会重开"。另外 `_mark_bootstrap_used` 写失败是 `except OSError: pass`，无日志。

修法：`_load()` 见非空账户表即补写标记；同时删掉 `host.py:1666-1670` 里为测试替身保留的 `except AttributeError` 旧口径分支（它正在被测试依赖，见 T-04）。

### auth-016｜中｜次版本门控只做在观看端，v2.2 客户端永久登录失败且丢凭据

`common.proto_compatible`（64-77）的注释就写着"主版本相同即兼容"，实现只判 `major == 2`，对次版本无门控；观看端却加了 `proto[1] >= PROTO_CHAL_MIN_MINOR(3)` 的单向要求（`viewer.py:872-875`）。

v2.2 的观看端按 `proto[1] >= 2` 判定"服务端支持挑战流"，但 v2.3 的 proof 输入串是 `HMAC(dk, "tv-auth-v2|" + user + "|" + nonce)`（`common.py:151`），旧端只签 nonce → host 校验失败 → 观看端命中 `viewer.py:965` 分支，**清空 `self.auth` / `_password` 并写回 config**：用户既登不上，又丢了已保存的口令，且界面提示（因 ui-026 的覆写）只会是套话。

修法：host 在 `AUTH_PROOF` / `REG_PROOF` 携带 `proto[1] < 3` 时回已有的"观看端版本过旧，请更新后重试"——观看端对该文案已能正确复位能力缓存（956-963），不会误清凭据。

### auth-017｜中｜输对口令也会被打断：首消息 30 秒档把用户输入时间算进去了

`host.py:1707, 1752` 的 `msg_deadline = min(deadline, monotonic() + AUTH_FIRST_MSG_S)` 从握手完成即开始计时，而 `viewer.py:1093-1151` 在 `_auth_probed` 为真且本地凭据已被清空时，**在发出任何字节之前**进入 `_ask_credentials()`：内部最长 60 秒等 root 就绪 + 120 秒等用户输入。

首次误输口令就会进入这个状态——host 回"用户名或密码错误"后观看端清掉 `username` / `_password`（976-985），下一次重连即走该路径。用户超过 30 秒才按下确定，`send_msg` 仍能成功但 `recv` 已超时 → 报"认证通信失败" → 弹框内容作废重来，循环往复。这是 auth-005 引入分档时口径的回退：第 31 条要求的"认证窗口必须覆盖用户输入耗时"在 probe 分支保住了（150 秒），首消息分支没保住。

### auth-018｜中｜登录报文的 `user` 没有长度上界，可把 32MB 写进日志

`MAX_USERNAME_LEN=64` 只加在 `register` / `register_derived` 的落库处（auth-006，`host.py:346/473`），`LOGIN` / `AUTH_PROOF` 的 `user` 字段没有校验，而 `recv_msg` 允许 `MAX_PAYLOAD = 32MB`（`common.py:198`）。已核实读取侧的 `_str_field`（`host.py:1677-1695`）**不带 max_len、不截断**，所以这条不是误报。回显 user 的失败分支在 **1853 / 1871 / 1900**，另有 1866、1893-1895（走 legacy 警告）与 `_auth_optional_phase` 的 1978——初稿写的 1808 是 `user = (raw_user or "").strip()` 赋值行，不是日志行。logger 不截断、滚动 5MB×5。

未认证的对端发一条 LOGIN（32MB 的 user）、收伪盐挑战、乱填 proof，即可在这一条连接上产出一条 32MB 的日志（recv 缓冲 + str + 格式化峰值约 130MB，且未认证名额允许 8 条并发），并把真实日志整体冲掉。属 auth-006 同类路径的口径遗漏——限制应加在读取处而不是只在写入处。

### auth-019｜低｜salt 形态不合规的账户永久登不进且零提示

`challenge_for`（`host.py:408-432`）只判 `isinstance(salt, str)`，缺 auth-006 配套的 `_is_hex_str(salt, 32)`；观看端在 `viewer.py:1034` 用 `_is_hex_str(salt, KDF_SALT_HEX_LEN)` 拒收，返回的 msg 不匹配 `_authenticate` 的任何已知分支，3 轮后 `return False`，而 `auth_msg` 又被 ui-026 改写成"需要登录后观看"，真实原因只进日志。同一记录走 legacy 路径则回"账号不存在"（枚举面残留，仅 `allow_legacy` 可达）。

`tests/test_d1_challenge_auth.py:407` 的 `assertIsNotNone(challenge_for("broken"))` 把这个缺口固化成了期望值（初稿把 169 行的 `assertNotIn("iter", ...)` 也算进来，那一句属 T-03 的口径、与本条无关）。触发需要手改配置或旧版本落盘的坏 salt（现行观看端恒发 32 位 hex），故定低。

### auth-020｜低｜观看端对"非法挑战参数"的捕获元组漏掉两类异常（初稿归因错位，已更正）

结论成立：中间人下发非法的 `iter` / `nonce` 时，异常会逃逸出 auth-002 精心准备的三条明确文案（iter 不符 / nonce 过短 / salt 非 hex），落到 `_authenticate` 的兜底变成"认证通信失败"+ 无限重连。实测（Python 3.13.9）：`{iter: Infinity}` 与 `{nonce: 123}` 均触发逃逸。

**但初稿把抛异常的地点写错了，导致给出的修法是错的**：

- 观看端在 `viewer.py:1012` 就先把 iter 过了一遍 `int()`——`int(inf)` 抛 `OverflowError`；`{nonce:123}` 则在 1011 行经 `b64d()` 抛 `AttributeError`（`common.py:169` 的 `text.encode`）。**两处都在真正调用 `derive_dk` 之前**（1039 行才调，且此时 salt 已过 1034 校验、iter 已是 int 且 ==100000，不可能再抛）。所以"把 OverflowError/AttributeError 并入 `derive_dk` 的捕获"**修不好本条**。
- 顺带更正两处引用：全仓不存在 `binascii.unhexlify` 调用（初稿举的 `unhexlify(123)` 是虚构示例，且该调用实测抛 `TypeError` 而非 `AttributeError`）。

正确修法：把 `viewer.py:1013` 的捕获元组补成 `(ValueError, TypeError, OverflowError, AttributeError)`（或直接 `Exception` 后按"服务端挑战参数异常"处理），并同步 `common.py:136-146` 的 docstring 使其只承诺实际会抛的类型。host 侧因 `_str_field` 预筛类型不受影响。

### auth-021｜中｜认证失败分支把最长 32MB 的 proof 整段 repr 写进日志

比 auth-018（`user` 通道）更省事的一条 32MB 日志放大路径，初稿漏记：`host.py:1829-1830`

```python
log.warning("auth proof 格式非法（%r）…", raw_proof, ...)
```

`raw_proof` 同样来自未认证对端可控的报文、长度只受 `MAX_PAYLOAD = 32MB` 约束，而 `%r` 会连引号与转义一并展开（体积还会略增）。触发只需三步：LOGIN → 收伪盐 CHAL（auth-014）→ 乱填 proof。相比 auth-018 少一步前提（不必让 user 字段穿过 `_str_field`）。其余口径同 auth-018：不截断、5MB×5 滚动、约 2 条/连接即可冲掉真实日志。

修法：与 auth-018 合并处理——所有进入日志的对端可控字符串统一 `repr` 前截断（例如 `_clip(text, 200)`），并给 proof/token 类字段固定只记前 8 位 + 长度。

### auth-022｜高｜`host.auth` 被写成非字典时，准入开关静默关闭（真正的 fail-open）

`host.py:1991-1997` 在 `_auth_required_phase` 取配置时把非字典的 `host.auth` 归一为 `{}` 处理，于是 `auth_cfg.get("enabled", False)` 取到 **False** → 直接走 `_auth_optional_phase`，**账户准入被关闭**；而同一份坏配置下的 `register_policy`（`common.py:345`）按缺键取默认 `"open"`。也就是说一条坏配置（把 `auth` 节写成字符串/数字/数组）会**同时关掉两道安全开关**：不再要求登录、且允许自助注册 —— 任何能连上的人都能自建账号看屏。**准确表述**：该分支并非完全无声，1993 行会记一条 `配置 host.auth 不是对象（…），按准入关闭处理` 的 WARNING；问题在于**安全开关的兜底取向是 fail-open**（与 auth-007 对 `allow_register` 取 fail-closed 的既定口径相反），且面板上的"账户准入"仍按另一套兜底显示，用户看不到自己已裸奔。

可达性已核实：`_deep_merge`（`common.py:1004`）只对 `None` 跳过，**非字典非 None 的值原样覆盖**默认字典；`_upgrade_config`（`1045`）只在 `isinstance(auth, dict)` 时才抬高 `enabled`，所以这条不会被迁移救回。初稿在第十三章写的是"非 dict 分支不构成越权"——**方向判断错了**，那句讨论的是 `register_policy` 返回默认 `open` 与出厂默认一致，但把它与"准入是否开启"混为一谈；实际后果见本条。

与 ui-022/ui-030 同属"配置子节不判型"族，但落点在安全开关上，故按安全后果定级为高。修法：`_load_config` 阶段就把所有"应为字典"的节做类型校验（非 dict → 回退默认 + WARNING），而不是让各读取点各自兜底；`enabled` 这类安全开关在配置异常时应取 **True**（fail-closed）。

### ui-021｜中｜观看端导出诊断包仍会冻结整个界面

## 八、配置、凭据与日志

### cfg-004｜高｜跨进程文件锁 fail-open，恰在设计目标场景失去保护

`_config_file_lock()`（`common.py:1172-1194`）等不到锁时 `return None`，而 `save_config()`（1239 行）拿到 `None` 之后**继续完成整份写盘**；`host.AccountManager._file_lock()`（`host.py:222-253`，`yield` 在 253 行）同样在超时后 `break` 并 `yield` 执行写。docstring 自述取向："宁可放行本次写（极小概率竞争），也不能让 GUI 线程永久卡死"。

问题是两个阈值互相打架：接管陈旧锁要求锁文件**年龄 > 10 秒**（`common.py:1185`、`host.py:240`），而等待方最多只等 **2 秒**。持有者崩溃或被强杀后的整个 10 秒窗口内，每个写入者都等 2 秒然后无保护地写——cfg-001 要根治的"host 与 viewer 整份回写互相陈旧覆盖"、auth-009 要根治的"双开实例下账户被静默抹掉"，恰好都落在这个窗口里。

更关键的是 Windows 语义：`os.remove()` / `os.replace()` 作用于仍被其它进程以句柄打开的文件会抛 `PermissionError [WinError 32]`（Python `os.open` 不带 `FILE_SHARE_DELETE`），而这里 `except OSError: pass` 直接吞掉——所以**活着的竞争者根本无法被接管**，fail-open 是必然路径而非小概率。

**更正初稿一处**：`host._file_lock` 的探针输出里"持有者已崩溃 → 也返回 None"那行是错的——探针自己还握着句柄，测的其实是活锁。补测：持有者进程退出后句柄即释放，锁龄 >10s 时可正常接管（`fd=4 after 0.00s`）。因此本条的两个真实洞应精确表述为：①**活锁永远接管不了**，竞争期间一律 fail-open；②持有者崩溃后的**前 10 秒**内，每个写入者仍会等满 2 秒然后无保护地写。实测（直接调用真实 `_config_file_lock`）：

```
held lock            -> None after 2.02s   # 活进程持锁：等 2s 后放弃，写盘照常进行、无保护
future-mtime lock    -> None after 2.01s   # 时钟前跳使年龄为负，接管判据不成立
持有者已退出(锁龄30s) -> fd=4 after 0.00s   # 正常接管（初稿此行记为 None 有误，见下）
```

次生影响：`save_config` 的调用点含 Tk 主线程回调（`host_ui.py:425/444/557`、`viewer.py:1848/1876/2872/2878`），锁竞争时每次写盘在界面上同步阻塞 2 秒。

修法：接管阈值必须小于等待上限（例如锁龄 >1s 即接管、等待 5s），或改为 fail-closed（拿不到锁就本次写失败并告警、由上层重试）；Windows 下应改用 `msvcrt.locking` / `LockFileEx` 这类字节范围锁，"排他创建 + 删除"对活进程既不能等待也不能接管。

### cfg-005｜低｜陈旧锁判定用墙钟，时钟后跳即推迟接管

`common.py:1185` / `host.py:240` 都是 `if time.time() - os.path.getmtime(lock_path) > 10.0`。锁文件 mtime 由写入时刻的墙钟决定，判定又用同一墙钟做减法：NTP 或手动校时把时钟往回拨 Δ，刚写下的锁在接下来 Δ 时间内算出**负年龄**，`> 10.0` 为假，接管被推迟 Δ。标题的"永不接管"按字面理解过强，准确说法是"回拨多久就延后多久"（探针把 mtime 设为未来 1 小时即复现）；另已核实该函数内**没有其它接管条件**（无 pid/存活检查）。同文件的等待逻辑已经用 `time.monotonic()`（1179、`host.py:232`），只有这一处判据漏网。修法：锁文件内写持有者 pid + 单调起点，并用 `os.replace` 的原子性做接管；或至少 `max(0, now - mtime)` 并同时检查持有进程存活。

### cfg-006｜低｜写失败的唯一临时名不清理，磁盘留下含明文 token 的残渣（"躲过卸载"一句已撤回）

同一个 cfg-001 修复里，`save_config` 的写盘分支有 `except OSError: os.remove(tmp)`（`common.py:1262-1266`），但 `_persist_upgrade`（1076-1086）与更新检查缓存两处只 `warning`、没有清理；由于临时名唯一（`config.json.<pid>.<tid>.tmp`），下次启动也不会覆盖回收，而是再落一个新名。`_replace_retry`（1211-1221）连抛 5 次 `PermissionError` 即走到该分支——而这正是函数自己承认的常态（杀软、另一实例持句柄）。**实测**：临时目录里 `_persist_upgrade` 失败后留下 `config.json.2584.14608.tmp`（内含明文 `SECRET-TOKEN`），同场景 `save_config` 的目录是干净的；`update_check` 的缓存同样不清理（留 `update_check.json.2584.14608.tmp`）。

### cfg-007｜中｜一个非法数值就能让整份用户配置被重置为默认

`common.py:1021`：`version = int(raw.get("config_version") or 1)`，而 `except` 只列 `(TypeError, ValueError)`。`Infinity` / `-Infinity` / `NaN` 是 Python `json` 默认接受的合法 JSON，`int(float('inf'))` 抛的是 **OverflowError** → 逃逸到 `load_config` 外层 `except Exception`（1142-1144）→ `_recover_corrupt_config` 把用户配置改名留存并写回默认值。

### cfg-008｜低｜`safe_int` 的 docstring 与实现相反

`common.py:734-760` docstring 首行："非法（字符串/None/布尔/**超出范围**）时**回退 default**"；实现末尾两行是 `if lo is not None and out < lo: out = int(lo)` / `if hi ... out = int(hi)`，即越界**钳制到边界**，`default` 完全不参与。实测：`safe_int(0, 5700, lo=1, hi=65535) -> 1`、`safe_int(True, 30, lo=1, hi=60) -> 1`。

### dist-009｜中｜更新检查号称"控制台勾选开启"，实际没有任何开启入口

`update_check.py:32-33` 与 `common.py:222` 的注释写着"需要更新提示时在共享端控制台勾选（或手改本键为 true）"。**更正出处归属**：初稿把 `docs/audit/dist.md` 也算作来源，实测该文件全文无"勾选"字样，dist-004 行只写了 opt-in。实测 `host_ui.py` 全文只有 `import update_check` 与 `start_background_check(...)` 两处，**没有任何 update_check 相关控件**（面板的 Checkbutton 仅 frp 自动启动、自适应、账户准入三处）。

于是 dist-004 把默认改成 opt-in 之后，opt-in 这条路对普通用户不可达：更新提示静默失效，而注释与审计记录在误导下一个读代码的人。功能门控本身是对的（默认关 + 缺键即关 + 两调用点都先过 `enabled()`），问题只在"开关只在 JSON 里"。

附带一条结构性隐患（本轮暂不计条，但须知道）：`_deep_merge` 是磁盘值优先，默认值翻转不会覆盖已有配置；`CONFIG_VERSION` 仍是 2 因此迁移分支不执行。当前**没有已发布版本会把 `enabled: true` 落盘**（`git show v1.3.0` 里既无 `update_check.py` 也无该配置节，已核实），所以存量用户不受影响；但下次再翻转任何安全默认时，这个模式就会成立。

### dist-010｜中｜安装包守卫只看两个 exe，空壳包仍能"构建成功"

`build_installer.bat:18-31, 80-85` 的 dist-002 守卫校验的是 `dist\fps-host\fps-host.exe`、`dist\fps-viewer\fps-viewer.exe` 存在 + 最终安装包 >1MiB。实测本仓两个 exe 分别 3,749,504 B 与 3,515,352 B（合计约 7.2MB），已远超 1MiB；而真正承载 `python3xx.dll` / `av.libs` / `numpy` 的是 `_internal` 目录，守卫不检查它，`installer.iss:34-35` 的 `dist\fps-host\*` 通配对"目录在、`_internal` 没了"也不报 warning。

结果：`_internal` 缺失（正是第 68 条 spec 被覆盖那一类事故）仍能编出"安装包已生成"并 exit 0，用户装完启动即 "Failed to load Python DLL"。实现方案 §1.1 自己写的验收标准是"≈111MB，偏差 >10%"，脚本没落实。修法：查 `_internal` 存在 + 总产物体积落在按版本记录的目标带（±10%）。

### dist-011｜低｜per-PID 日志文件数无上限

`logger.py:73` 每个进程一个 `app_<日期>_pid<N>.log`，`_prune_old`（75-106）按**日期整组**保留 `_KEEP_DAYS=5`，组内不限量，且每份还能滚出 `.1~.5` 五个备份。docstring 写"避免磁盘无限增长"，实际增长维度换成了"启动次数"。实测本机 `logs/` 共 191 个文件，其中 2026-09-11 单日 69 个且 69 个 PID 互不相同（开发机常态）。

**比"组内不限量"更根本的一层（初稿漏掉）**：`keep_keys = sorted(groups)[-5:]` 保留的是"目录里现存的后 5 个日期组"，而**不是"距今 5 天"**。本机现存 20260911/17/18/19/20 五组，于是最旧的（9 天前）那组也被完整保留、实删 0 个文件——组间不限龄才是 191 这个数的直接成因。修法应与 dist-014 一并做：按"距今 N 天"筛日期组，组内再按总量裁剪。配合崩溃循环，上限是"日期数 × 每日启动次数 × 6 × 5MB"。与 dist-014 同源。修法：按总数/总字节再做一层裁剪。

### dist-012｜中｜签名脚本硬编码 1.4.0，版本 bump 后安装包会被静默跳过

`sign_exe.ps1:21` 的默认待签清单写死 `'dist\TeamVision-Setup-1.4.0.exe'`；"文件不存在"的处置在 `Invoke-SignOne`（**97-103 行**，初稿误写 118-124，那是时间戳重试段）——只打一行 `[跳过]` 并返回 `$null`，主流程记为 `skip++`、不计 `fail`，脚本最后 `成功 2 / 失败 0 / 跳过 1` 并 **exit 0**。

**触发条件要比初稿收窄**：`installer.iss:19` 的 `OutputBaseFilename=TeamVision-Setup-1.4.0` 与 `sign_exe.ps1:21`、`build_installer.bat:75/80/86/88` **当前是一致的**（`dist/TeamVision-Setup-1.4.0.exe` 实存 116,374,504 B），而且 `build_installer.bat:87-88` 显式传 `-Files` 覆盖默认清单——走正常打包链时不会命中。真正会命中的只有两条路：①版本 bump 时改了 iss+bat 而漏改 ps1；②照脚本头注释的用法**无参直跑** `sign_exe.ps1`（默认清单此时才生效）。仍值得修，理由不是"天天踩"，而是**一旦命中失败模式是静默成功**：未签名的对外产物会带着 exit 0 出门。这是第 67 条"版本号多处漂移"的真实危害面——不是"看起来不整齐"，而是会静默产出不该发布出去的产物。另外 `Invoke-SignOne` 把 `UnknownError` 当成功放行：自签证书未入信任链时合理，但 CA 证书出现 `UnknownError`（时间戳服务不可达等）同样被放行，建议只对"本机自签"放宽。

修法：默认清单改为通配 `dist\TeamVision-Setup-*.exe` 或从 `common.APP_VERSION` 取版本；"应签文件不存在"记为失败。

### dist-013｜低｜`setup.bat` 默认第三方镜像且对 HTTPS 源加 `--trusted-host`

`setup.bat:10`（TUNA conda 通道）与 `:11`（阿里云 pip 源，并带 `--trusted-host mirrors.aliyun.com`）——初稿写的 11-12 偏了一行。源本身是 HTTPS，`--trusted-host` 在这里只起"跳过该主机证书校验"的降级作用，没有额外收益。与项目既有约定（官方源分步直连优先，使用国内镜像需显式授权）也不一致。建议默认走官方源，镜像改为显式开关，并去掉 `--trusted-host`。

### dist-015｜中｜bat 以 UTF-8 无 BOM 保存 + `chcp 65001`，实测会破坏命令边界

初稿在第十三章把这件事当作"已核查无问题"记录（原文：噪音只落在 `rem`/`echo` 文本行、未打断守卫）。**复核推翻了这个结论**，故在此单列并撤销该条 clean-bill。

复现（TEMP 沙箱、按原字节复制运行两支 bat）：cmd 在 `chcp 65001` 下按**字节**读取脚本、却按控制台码页解析行边界，导致行长度发生变化时出现真正的语义错位——一次运行中 `if … (` 块的**全角 `）` 被吞掉**，且**后续一行被并进前一条 `echo`**（实测把 `powershell … sign_exe.ps1` 拼进了"安装包已生成…"的 echo 参数里）。也就是说受影响的不只是注释与提示文字，**命令行本身会被改写**。两次运行最终 exit 码碰巧仍正确，属侥幸而非机制保证。

风险定位：日常不发作，但**任何人改动这两支 bat 的行长度**（尤其中文注释/提示增删）都可能让某条命令被静默吞并或错位，而 `build_installer.bat` 里恰好是签名与守卫逻辑所在。修法：脚本改用 GBK(936) 保存并去掉 `chcp 65001`，或改存 UTF-8 **带 BOM**；更彻底的做法是把这两支 bat 的逻辑迁到 PowerShell 脚本（仓库已有 `sign_exe.ps1` 的先例）。改完后需重新实测一次守卫路径（产物缺失 / 200B 假包 / 正常三条）。

### dist-014｜高｜诊断包只收当前 PID 的日志，而它的使用场景恰恰是"上一个进程已经崩了"

`diag.py:49-79`：`recent_log_files(..., pid=...)` 用 `_pid_matches` 按文件名里的 `_pid<os.getpid()>` 过滤，PID 是 `logger.py:73` 建 handler 时定死的；第 74 行 `if pid is not None and not _pid_matches(...): continue`。

崩溃 / 闪退 / 按 FAQ"重启后再试一次"的用户，导出诊断包时进程已经换了 PID，`recent_log_files` 返回空列表，`build_report_zip`（135-140）只是不追加文件，照样 `os.replace` 出包、返回成功路径，report.txt 里也没有"日志缺失"这一项——**包打不开问题，因为它把唯一能说明问题的东西过滤掉了**。实测本机单日就有 69 个不同 PID 的日志文件，任一非当前 PID 都被排除。

第二条触发路径：`logs_dir` 固定取 `data_dir()/logs`，而 logger 在不可写时会回退到 `exe_dir()/logs` 或 `%TEMP%\TeamVision-logs`（`logger.py:184-185`）→ 日志确实在磁盘上，却收不到。`tests/test_diag.py` 全篇不传 `pid=`，该分支零覆盖（见 T-08）。

说明这条为什么定高：这是第 5 轮 auth-012 为"两端日志混包泄露"引入的回归——防泄漏的目标确实达成了（包内 `config.json` 经 `redact()`，探针实测零泄漏），但把诊断能力一起关掉了。修法：取"本进程 + 上一次进程"的 PID 集合，或按 mtime 取最近 N 个，并在 report.txt 里显式写明收到/缺失哪些文件。
