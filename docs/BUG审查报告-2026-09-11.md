## 1. 🔴 高严重程度

> 本节把 **A0** 放在最前：它由用户报告、经本机**实测定位并复现**，是唯一已被证实正在造成用户可见故障的缺陷（frp 隧道下完全看不到画面），优先级高于其余所有条目。

### A0｜frp 内网穿透下「视频画面无法传递」——`127.0.0.1` 只绑 IPv4，而 frpc 回连走 `::1`（实测定位）

**用户报告**：走项目配置的公网穿透地址 `[隧道域名]:[公网端口]` 时，视频画面无法传递。

**位置**：

| 文件 | 行 | 内容 |
|---|---|---|
| `host.py` | `1797-1810` | `_listen_target()`：`bind_all = listen_host in ("", "0.0.0.0", "::")`；非 bind_all 时按 `':' in listen_host` 选地址族 |
| `host.py` | `1875-1881` | `bind_listener()`：`family = socket.AF_INET6 if ":" in listen_host else socket.AF_INET` → **`"127.0.0.1"` 走 AF_INET，只绑 IPv4 回环** |
| `common.py` | `597-624`、`78` | `DEFAULT_CONFIG["host"]["listen_host"] = "127.0.0.1"`；`_upgrade_config()` 会把用户原来的 `0.0.0.0` **一次性迁移**成 `127.0.0.1` |
| `host.py` | `2041-2045` | `_log_security_notice()` 打印「监听 127.0.0.1:5700（**仅本机与 frp 隧道可达**）」——这句在故障状态下是**错误结论** |

**现象（两端 + 第三方日志，全部实测）**：

1. 观众端（`%LOCALAPPDATA%\TeamVision\logs\app_20260911_pid48824.log`）——每一次都停在**握手指令之前**：

   ```
   16:32:47 频道[频道1] 正在连接 [隧道域名]:[公网端口] …
   16:32:47 [WARNING] 频道[频道1] 连接断开: 连接提前关闭，收到的数据不完整
   16:33:12 [WARNING] 频道[频道1] 连接断开: 连接提前关闭，收到的数据不完整
   16:33:45 [WARNING] 频道[频道1] 连接断开: 连接提前关闭，收到的数据不完整
   16:33:45 频道[频道1] 30.0 秒后重新连接…
   ```
   （`连接提前关闭，收到的数据不完整` 来自 `common.recv_exact`：TCP 已建立，但没等到 `OK02` 就被对端关闭。）

2. 共享端（`...\logs\app_20260911_pid45568.log`，全程 `listen 127.0.0.1:5700`）——**整场只有 1 条客户端接入记录，是 127.0.0.1 的本地频道；隧道方向的连接一条都没到，连 `握手失败` 都没有**：

   ```
   16:32:35 服务已启动，监听 127.0.0.1:5700
   16:32:58 客户端接入: ('127.0.0.1', 58451)（alice，当前 1 个客户端）   ← 唯一一条
   16:33:55 客户端断开: ('127.0.0.1', 58451)（alice，接收错误，累计发送 3.3 MB）
   ```
   即：**本地频道正常收流 3.3 MB，隧道频道一个字节都没进来。**

3. 樱花 frpc 自己的日志（`C:\ProgramData\SakuraFrpService\logs\SakuraFrpService.20260911.log`）给出了中间那段缺失的真相——**时间戳与观众端的失败一一对应**：

   ```
   使用 >>[隧道域名]:[公网端口]<< 连接你的隧道
   2026/09/11 16:32:47 [E] [85/[隧道ID]/d2f6] 连接映射目标 [tcp://localhost:5700] 失败, 请检查本地服务是否可访问 … 错误信息: 连接被拒绝, 目标端口可能未打开
   2026/09/11 16:33:12 [E] [85/[隧道ID]/d2f6] 连接映射目标 [tcp://localhost:5700] 失败 …
   2026/09/11 16:33:44 [E] [85/[隧道ID]/d2f6] 连接映射目标 [tcp://localhost:5700] 失败 …
   ```

**根因**：**frpc 的本地目标是 `localhost`，Windows 上 `localhost` 的解析顺序是 `::1` 优先**；而共享端在 `listen_host = "127.0.0.1"` 下**只绑了 IPv4 回环**，`[::1]:5700` 无人监听 → frpc 被拒 → 樱花节点关掉公网连接 → 观众端停在握手前 → **画面完全传不过来**。

> 说明（避免过度断言）：frpc 具体挑 `::1` 还是 `127.0.0.1` 取决于它的解析/连接策略（本次实测落在 `::1`；09-11 08:00 那次 `listen_host=0.0.0.0` 的运行里，双栈 socket 收到的连接显示为 `('::ffff:127.0.0.1', …)`，说明它也可能走 IPv4）。**关键不在于它挑哪个，而在于「只监听 IPv4 回环」必然漏掉 `::1` 这一半，而双栈监听两种都覆盖**——这也是 A0 修复方案之所以是"回环双栈"的原因。

**本机实测复现（决定性证据）**：

```
localhost 解析顺序： AF_INET6 ('::1', 5700, 0, 0)  →  AF_INET ('127.0.0.1', 5700)

实验 A：只监听 IPv4 127.0.0.1:5700（＝迁移后的默认配置）
        公网侧连 [隧道域名]:[公网端口] → 收到 b''（对端关闭）
        本地监听 12 秒内没有任何连接到达        ⇒ 隧道不可达 ✗
        同时 frpc 日志新增一条 "连接映射目标 [tcp://localhost:5700] 失败 … 连接被拒绝"

实验 B：双栈监听 ::（＝ listen_host 为 0.0.0.0 时的行为）
        公网侧连 [隧道域名]:[公网端口] → 收到 b'OK02'（握手成功）
        本地监听收到来源 ('::1', 50692, 0, 0) 的隧道连接，魔数 b'FS02'  ⇒ 隧道可达 ✓
```

**为什么这次改动把它弄坏了（代码自相矛盾之处）**：`_listen_target` 的注释**早就写明了这条规则**——

> 第 19 条语义：bind_all（""/"0.0.0.0"/"::"/None）→ 双栈 socket，一个端口同时覆盖 IPv4/IPv6（**frp 本地回连在 SYSTEM 上下文优先走 ::1，必须双栈，否则公网链路握手即断**）；指定具体地址（如 127.0.0.1）→ 只绑该地址、该地址族，真正把共享限制在本机。

而第 131 条「更安全的默认值」把 `listen_host` 默认值改成 `127.0.0.1`，并在首次启动时**把用户原来的 `0.0.0.0` 静默迁移成 `127.0.0.1`**（`_upgrade_config`，日志里能看到「配置已升级到 v2：监听地址 0.0.0.0 → 127.0.0.1」）。于是**默认形态（也正是文档推荐的公网共享形态：共享端只监听 127.0.0.1 + 樱花 frp）从设计上就不可能工作**：一边要求「frp 必须双栈」，另一边把默认值改成「只绑 IPv4」。本地自测不会发现，因为本地观众端填的是 `127.0.0.1`，走 IPv4 一切正常。

**触发条件**（本机恰好全部满足，且在真实用户环境里很常见）：

1. `host.listen_host` 为 `127.0.0.1`/`localhost`/`::1` 等**具体回环地址**（第 131 条之后这是默认值）；
2. 樱花控制台里隧道的**本地地址填的是 `localhost`**（樱花创建隧道时的默认写法，日志显示 `tcp://localhost:5700`）；
3. frpc 由 **SakuraFrpService 以 Windows 服务（SYSTEM / 会话 0）** 拉起 —— 即 `FrpManager._sakura_service_running()` 检测到的那种形态；
4. 本地 `localhost` 解析优先返回 `::1`（Windows 默认行为）。

**影响**：**公网共享功能完全不可用**，而两端所有界面与日志都显示「正常」——共享端显示「监听 127.0.0.1:5700（仅本机与 frp 隧道可达）」、`frp` 显示「运行中」、本地频道画面流畅；观众端只报一句无法归因的「连接提前关闭，收到的数据不完整」，且**共享端侧零日志**（连接根本没到达进程）。这是最难排查的一类故障（用户只能"盲猜"是网络问题）。

**修复建议（按推荐度排序）**：

1. **正解**：`_listen_target` 把回环别名视作「回环双栈」——当 `listen_host ∈ {"127.0.0.1","localhost","::1"}` 时，同时监听 `[::1]:port` 与 `127.0.0.1:port`（两个 socket 都只绑回环，**不降低安全性**），`_accept_loop` 对两个监听 socket 一起 select。这样既保住"只允许本机与 frp 隧道"的安全姿态，又覆盖 frpc 的 `::1` 回连。
2. **低成本兜底**：启动时自检并告警——若 `listen_host` 是具体回环地址**且** `host.frp` 配了 token/tunnel_ids/public_addr，则写一条 WARNING：「frpc 常以 `localhost` 回连，会优先走 `::1`；当前只监听 IPv4 回环，隧道将连不上本机。请把樱花隧道的本地地址改为 `127.0.0.1`，或把监听地址设为 `0.0.0.0`」。
3. **修正迁移策略**：`_upgrade_config` 在把 `0.0.0.0` 改成 `127.0.0.1` 时，若检测到 `host.frp` 有实际隧道配置，应保留 `0.0.0.0`（或同时提示"公网共享将失效"），而不是静默迁移。
4. **同时修文案**：`_log_security_notice` 的「仅本机与 frp 隧道可达」在第 2 项自检为真时应改成明确的风险提示；`docs/部署操作文档.md:168`「frpc 走 `127.0.0.1` 依然能连上」这句**是错的**（樱花默认写的是 `localhost`，走 `::1`）——见下方「附带发现的文档错误」。

**用户当下可用的绕过办法（任选其一）**：

- **最省事**：到樱花控制台把该隧道的**本地地址由 `localhost` 改为 `127.0.0.1`**（显式 IPv4 字面量就不会走 `::1`），重启隧道即可；
- 或把共享端「传输参数 → 监听地址」改成 `0.0.0.0` 并**重启共享端**（能通，但局域网内所有人可达该端口，安全性下降，需要配合账户准入）；
- 或改用局域网直连/其他隧道形态（同样受监听地址影响）。

**为什么现有测试没拦住**：357 项回归里没有任何一项覆盖「frpc 以 `localhost` 回连 → 命中 `::1`」这条真实链路；`tests/test_item131_hardening.py` 只断言了「默认值迁移成 127.0.0.1」，反而把错误默认值**固化**进了回归。

### A1｜上行限速令牌桶的补充速率是名义值的 2 倍

**位置**：`host.py:329-352`（`ClientInfo.allow_upstream`），关键两行：

```python
337:  burst_bytes = max(1.0, max_kbps * 250.0)   # kbps -> bytes/s = ×1000/8，容量 2 秒
...
344:  self._up_tokens = min(burst_bytes, self._up_tokens + elapsed * burst_bytes)   # ← 补充量 = elapsed × 容量
345:  self._up_frames = min(max_fps, self._up_frames + elapsed * max_fps)
```

**现象**：`max_kbps` 对应的字节速率是 `max_kbps × 1000 / 8 = max_kbps × 125` 字节/秒；代码把"2 秒额度"（`max_kbps × 250` 字节）**当成了每秒补充速率**，于是桶的持续补充速度是名义值的 2 倍。字节桶的实际长期吞吐上限约为 `2 × upstream_max_kbps`。

对照组：同一函数里的帧率桶（345 行）容量 = `max_fps`、每秒补充 = `max_fps`，容量与速率一致——只有字节桶算错了。

**触发条件**：任何观看组成员持续上行接近（但不超过）配置上限时即生效；订阅者越多、上游越激进，越容易观测到。

**影响**：

- 第 107 条（B8）引入该令牌桶的目的正是限制"单个成员把上行流量 1:N 放大到所有订阅者"（每帧都要 host 复制给每个订阅者）。现在这道护栏的实际额度翻倍，恶意/异常成员可以把 host 的上行带宽与 CPU 消耗推到设计值的 2 倍。
- 数值复现（300 帧 @30fps、每帧 8 KB、`upstream_max_fps=60`）：

  | `max_kbps` | 放行帧数/总帧数 | 实测吞吐 | 相对名义上限 |
  |---|---|---|---|
  | 600 | 205 / 300（10 s） | 1312 Kbps | **2.19×** |
  | 2500 | 300 / 300（10 s，未打满） | 1920 Kbps | — |

  600 Kbps 档下 10 秒内放行量已达名义上限的 2.19 倍（含首帧的 2 秒突发），长期收敛到 2.0 倍。

**现有测试为何没抓到**：`tests/test_optimize_stage1.py:887` 的 `test_byte_bucket_throttles_then_refills` 注释明确写着「1 秒后补 12500 字节额度」（即 100 Kbps = 12500 B/s，正确意图），但断言只检查"6000 字节被放行"——而代码实际补了 25000 字节，同样放行。断言弱于注释意图，因此该 bug 未被回归覆盖。

**修复方向**：补充量改为 `elapsed * (burst_bytes / 2)`（或把 `burst_bytes` 拆成 `rate_bytes_s = max_kbps * 125` 与 `capacity = 2 * rate_bytes_s` 两个变量，补充用前者、削顶用后者）；并给该测试补一条"补满 12500 字节后应恰好拒绝第 12501 字节"的强断言。

### A2｜采集后端启动即失败时，`host._capture_loop` 永久无法自愈并刷日志

**位置**：`pipeline.py:280-291`（`CaptureSource.set_params`）+ `host.py:1984-1989 / 2001-2002`



**现象**：`CaptureManager` 在 dxgi 与 mss 都初始化失败时只把句柄置 `None`（不抛异常）。此后 `CaptureSource.cap is None`，而 `_capture_loop` 每轮先调 `set_params` → 命中 `self.cap.set_params` 的 `AttributeError` → 返回 `False` → `continue`。

- 共享端**永久无画面**，只有重启进程才能恢复；

- 与 `share.py:126-129` 的处理形成对比——上传会话在同样情形下会"报错并停止"，不会假装存活。

**修复方向**：`CaptureSource.set_params` 在 `self.cap is None` 时改为走 `_rebuild("采集句柄缺失，尝试重建采集器")` 并返回重建结果（布尔），让 `_capture_loop` 既能看到失败、又能触发重建；同时给该 warning 加去重（如 10 秒一次）。

### A3｜凭据请求队列淘汰最旧请求却不唤醒其等待者；该等待不可被停止打断

**位置**：`viewer.py:829-846`（`Channel._ask_credentials`）

```python
834:  try:
835:      while owner._cred_requests.qsize() >= 4:
836:          owner._cred_requests.get_nowait()      # ← 丢弃最旧请求，但不 set 其 done
837:  except queue.Empty:
838:      pass
839:  owner._cred_requests.put((self, done, box))
840:  done.wait(timeout=120)                          # ← 接收线程在此阻塞最长 120 秒
```

**现象（两个耦合缺陷）**：

1. **淘汰不唤醒**：队列限长 4 时被丢弃的请求，其 `done` 事件永远不会被置位（`_process_cred_requests` 也从队列里取不到它了），该频道的接收线程只能**等满 120 秒**才返回。原注释假设"其等待者已超时或即将超时"，但被淘汰的很可能是刚入队 1 秒的请求——多频道（≥5 个）同时需要登录时必现。
2. **等待不可中断**：`done.wait(timeout=120)` 不受 `_running` / `_stop_evt` 影响。`Channel.stop()`、`request_stop()`、`ViewerApp.remove_channel()` 都无法打断它，于是"删除一个正在等登录的频道"后，`channel-recv` 线程与其持有的 socket 会**残留最长 120 秒**（B13 已把退避等待改成可中断的 `Event.wait`，但这条路径漏了）。

**触发条件**：服务端开启账户准入且有多个频道（或反复重连）同时进入登录流程；以及用户在登录框等待期间删除/重建频道。

**影响**：多频道场景下部分频道的登录/重连被无谓推迟 2 分钟（表现为"某个频道一直连不上，过两分钟自己好了"）；删除频道后线程与 fd 残留，长跑会话下反复"删了再加"会累积同名线程（正是 B13 想消除的现象）。

**修复方向**：

- 淘汰时一并 `done.set()`（或给淘汰项写入 `{"result": {"error": ...}}`），让等待者立刻返回；
- `done.wait` 改为循环 `while not done.wait(0.5): if not self._running: return None`，或在 `Channel.stop()` 里对未完成的请求置位 `done`；
- 更彻底：把 `_ask_credentials` 的等待拆成"入队 + 可中断等待"两段，用 `_stop_evt` 一并唤醒。

### B8｜共享会话自行终止时既不通知对端（`unshare`）也不通知本端 UI → 主机 roster 里长期挂着"死源"

**位置**：

| 文件 | 行 | 内容 |
|---|---|---|
| `share.py` | `126-129` | `if not src.working(): log.error(...); self._close_resources(); return` —— **显式停止，但不发 `unshare`、不回调上层** |
| `share.py` | `169-170` | `finally: self._close_resources()` —— 任何退出路径都不通知 `Channel` |
| `viewer.py` | `1047-1059` | `_maybe_resume_share()` 只在收到 `cap`/`peers` 或重连时才有机会发现会话已死；连接保持期间不会再检查 |
| `host.py` | `932-951` | `share_id` 只在 `unshare`、连接断开（`_client_teardown`/`_drop_client`）两条路径上注销 |

**现象**：`ScreenShareSession` 的线程可能因为下列原因终止而**连接仍然健在**——① 采集后端不可用（`src.working()` 为假）；② 循环内编码/采集持续性失败；③ 线程因未预期异常退出。此时：

- **对端（共享端 host）不知道**：`ClientInfo.share_id` 仍是 `peer:N`，该成员继续留在**所有观众端**的「画面源」列表里。别的观众选中它之后**永远收不到一帧**（停在最后一帧或全黑），界面无任何提示——因为 host 侧并不存在"这个 peer 已经不产帧了"的判定（`_allow_upstream` 的丢帧计数只在超限时告警，且是共享端本地日志，观众端看不到）；
- **本端（共享者）也不知道**：`Channel.share_enabled` 仍为 `True`，面板按钮仍显示「停止共享」，用户以为自己在共享，直到手动点一下或重连才自愈（`_start_share` 发现 `alive` 为假会重建）。

**触发条件**：共享端（成员）一侧采集链路失效（例如无显示的会话/RDP 下 `mss.MSS()` 也失败，或 dxgi/mss 都不可用）、或上传期间发生连环编码失败。属"低概率但零可观测性"的一类故障。

**影响**：多画面源（MultiView）场景下出现"幽灵源"——观众看到的是一个永远不更新的源，且被算进 roster；共享者则在不知情的情况下停止共享。与第 56 条/B3（转达关键帧请求时成员掉线不拆观看者）属同一族：**成员侧状态变化缺乏向 host 与 UI 的传播**。

**修复方向**：

1. `ScreenShareSession` 增加 `on_terminate(reason)` 回调（或在 `_run` 的 `finally` 里置一个 `self.exit_reason`），由 `Channel` 在检测到 `not session.alive` 时：`share_enabled = False` → 面板提示「共享已停止：<原因>」→ 若连接仍在则补发一次 `{"action":"unshare"}`；
2. `Channel` 的 `poll`/面板刷新周期里加一条廉价检查（`if self.share_enabled and self._share is not None and not self._share.alive: 处理`），把"会话已死"从"要等下一次 cap/peers"变成"最长一个刷新周期内自愈"；
3. 共享端侧可对 `share_id` 加"最近一次上行帧时刻"，超过 N 秒（如 10 s）未收到该成员任何帧就在 roster 上标注/剔除，避免"死源"被反复选中。

### B9｜「发送帧率」与实际订阅者脱钩：无任何观众时 ABR 仍会把码率顶到上限并反复强制 IDR

**位置**：`host.py:2225-2271`（`_send_loop` 无条件统计 `send_fps`/`avg_send_ms`）+ `host.py:2492-2497`（`_abr_recover` 的 `stats["send_fps"] >= 5` 门槛）

**现象**：`_send_loop` 的 `send_window` 记录的是"发送线程处理了多少帧"，**与 `route_frame` 是否真的投递给了客户端无关**（没有客户端时 `route_frame` 直接返回，但 `send_start`/`send_ms`/`send_fps` 照常统计）。于是零观众时 `send_fps ≈ 27`、`effective_send_ms ≈ 0`，恰好满足 `_abr_recover` 的回升条件（`send_fps>=5 且 无丢帧 且 发送耗时 < budget/2`），ABR 每秒把码率 ×1.3 直到 `max_bitrate`，每次 `_set_encoder_bitrate` 又会 `force_key = True` **强制一帧 IDR**。

**证据**（本次真实运行 `%LOCALAPPDATA%\TeamVision\logs\app_20260911_pid45568.log`，**第一个观众在 16:32:58 才接入**）：

```
16:32:35,500 启用视频编码器: hevc_nvenc（854x480，码率 2500 Kbps，keyint 60）
16:32:36,252 ABR 码率调整: 3250 Kbps（编码器重建，下帧关键帧）
16:32:36,257 静止期响应关键帧请求（76058 字节）      ← 强制 IDR，无人观看
16:32:38,359 ABR 码率调整: 4225 Kbps（编码器重建，下帧关键帧）
16:32:38,364 静止期响应关键帧请求（93833 字节）      ← 越来越大
16:32:40,496 ABR 码率调整: 5492 Kbps（编码器重建，下帧关键帧）
16:32:40,503 静止期响应关键帧请求（99512 字节）
16:32:58,591 客户端接入: ('127.0.0.1', 58451)        ← 观众此刻才来
```

即：**在没有任何订阅者的 11 秒里**，码率被抬到 5492 Kbps（接近上限 6000），并白白编码/发送了 3 个 76–99 KB 的强制 IDR；观众到来时继承的是一个 **5.5 Mbps** 的目标码率（而实测链路只有 ~450–880 Kbps），在带宽受限的公网隧道下正好触发"拥塞→降级→回升"的往复。

**触发条件**：启动后尚未有观众的空档期（常态）、或观众全部离线而服务仍在跑（夜间挂机）。

**影响**：无观众时也在持续做无谓的编码与关键帧突发（CPU/GPU 与"最后一帧"带宽浪费）；首个观众从更高码率起跳，加重弱链路拥塞；日志里表现为"码率一路上调"与"静止期响应关键帧请求"交替出现，容易误判为真实网络波动。ABR 的 `send_fps>=5` 门槛本意就是防"把停发误判为空闲"，但它用的是**发送线程自己的计数**，没能识别"根本没人订阅"。

**修复方向**：把"是否有活跃订阅者"纳入判据——例如 `route_frame` 返回本次实际投递的客户端数（或 `_send_loop` 用 `len(runtime.clients) > 0 and 有客户端且 watch_source 命中` 判断），无订阅者时冻结 ABR（与 `stats["still"]` 的处理同样直接 `return`）；`_set_encoder_bitrate` 的强制关键帧在无订阅者时也可跳过。

### B10｜安全迁移会把用户推进"输对了也登录失败"：`auth_timeout` 无下界约束，而随包 `config.json` 恰是 60 秒

**位置**：

| 文件 | 行 | 内容 |
|---|---|---|
| `common.py` | `78`、`620` | `DEFAULT_CONFIG` 里 `auth_timeout = 150`，注释明确写着"**须大于观看端登录框等待（120s）**，否则用户还在输入 host 就先断开、明明输对却登录失败（第 31 条）" |
| `common.py` | `597-624` | `_upgrade_config()` 只把 `listen_host` 与 `auth.enabled` 迁移到安全默认值，**不动 `auth_timeout`** |
| `host.py` | `1224` | `auth_timeout = _safe_float(auth_cfg.get("auth_timeout", 150), 150, **1**, 3600)` —— **下界是 1 秒**，任何比客户端等待更小的值都被接受 |
| `viewer.py` | `818-846` | 客户端真正发出凭据前的等待 = 等 Tk 就绪（最长 60 s，见 C19）+ 登录框 `done.wait(120)` → **最坏 ≈180 s** |
| `config.json` | `53` | 仓库里随包的开发配置写的是 **`"auth_timeout": 60`** |

**现象**：第 131 条的迁移会在首次启动时**自动把 `auth.enabled` 从 false 改成 true**（本机日志可见：`配置已升级到 v2…账户准入 关闭 → 开启`），但并不校正 `auth_timeout`。于是：

- 随包 `config.json`（`auth_timeout: 60`）被迁移后 → 准入开启 + 认证窗口 60 s。`_auth_required_phase` 的 deadline 从**连接建立时**起算，而观众端可能仍在"等界面就绪 + 等用户填用户名密码"（最坏 ≈180 s）→ 用户还在输入，服务端已经 `客户端 X 未在 60 秒内完成登录，已断开`；
- 观众端表现为 `认证通信失败` / 反复弹登录框（`_prompt_blocked_until` 还会叠加 30 s 冷却），**正是第 31 条当年修掉的故障模式，被这次迁移重新引了回来**；
- 默认 150 s 其实也**小于**客户端最坏 180 s（120 + 60），余量只有 30 s，慢用户/公网高延迟下同样可能踩到。

**触发条件**：配置里 `host.auth.auth_timeout` 小于客户端等待时间（随包配置就是 60）；且 `auth.enabled` 为真（迁移后默认即为真）。公网隧道场景（观众端在被穿透后的高延迟链路上手输凭据）最容易命中。

**影响**：准入开启后"第一次连接必失败、要弹两次框"甚至彻底登不进去，用户会误以为密码错或账号没注册，而共享端日志里只有一条"未在 N 秒内完成登录"——与密码无关，但提示看起来像认证失败。

**修复方向**：

1. `_safe_float(auth_cfg.get("auth_timeout", 150), 150, **低界应≥客户端等待上限**, 3600)`——把下界提到能覆盖 `等待界面就绪 + 登录框等待`的值（建议 ≥180 s，或让客户端等待显式小于服务端窗口）；
2. `_upgrade_config` 在把 `auth.enabled` 改成 true 时，若 `auth_timeout` 低于该下限，**一并抬高并在日志里说明**（迁移的目标是"更安全"，不该顺手把可用性弄坏）；
3. 随包 `config.json` 的 `auth_timeout: 60` 应改为 150（或直接删掉该键，留空走默认值），避免它成为迁移后的实际取值；
4. 观众端可把"等界面就绪"的 60 s 上限改为在认证窗口内自适应（例如把 `mainloop_ready` 与 `done` 两次等待合并为一个受 `_stop_evt` 驱动的等待链）。

## 3. 🟡 低严重程度（健壮性 / 一致性 / 可维护性）

### C1｜host 侧 socket 超时被永久改写且不还原，违反项目自订的"阻塞基线"不变量

`host.py:358-373`（`ClientInfo.send_ctrl`）与 `host.py:474`（`_client_sender_loop`）都把 `sock.settimeout(2.0)` 写进 socket 后**不还原**。而 `viewer._send_locked`（`viewer.py:537-568`）与 `share._send_msg`（`share.py:237-260`）都为此写了"保存原超时 → 临时收紧 → finally 还原"，注释（第 96 条）明确说明"接收循环的阻塞基线必须保持"。host 侧接收循环用 `select` 门控 `recv`，当前实现下未观测到故障，但该不变量已被破坏：一旦后续在 recv 路径引入依赖"阻塞模式"的逻辑（或某平台 select/recv 语义差异），就会踩到"合法慢速连接被误判为接收错误"。建议与 viewer 同一写法（锁内保存/还原）。

### C2｜`_client_recv_loop` 的 `partial_since` 计时起点可能偏早

`host.py:1454-1455`、`1480-1481`：`partial_since` 只在"本段数据到达前缓冲区为空"时设置。若一段 `recv` 同时"凑完上一条消息 + 留下下一条消息的半截"，`partial_since` 仍保留**上一条消息首字节**的时刻 → 第二条消息的"单条消息总时限（`msg_timeout_s`，默认 15 s）"被提前起算，理论上可在只收到它一小部分时被判定超时断开。窗口很窄（需一条消息分片跨 15 s），影响有限；`msg_timeout_s` 调小或大帧跨慢链时概率上升。建议在"消费完消息后缓冲区非空"时重置为当前时刻。

### C3｜`logger._prune_old` 用 `name[4:12]` 当日期分组键，非日期文件会挤掉真实日志

`logger.py:74-90`：`files = [f for f in os.listdir(...) if f.startswith("app_") and ".log" in f]`，随后 `date = name[4:12]` 分组、`keep_keys = set(sorted(groups)[-_KEEP_DAYS:])`。目录里若存在 `app_debug.log` 之类的非日期命名文件，其"日期"键 `"debug.lo"` 在字典序上大于任何 `"2026xxxx"`，于是**被保留在 keep_keys 里，而某个真实日期组被挤出 5 日窗口删除**（日志丢失）。建议用正则严格匹配 `app_(\d{8})` 并忽略不匹配的文件。

### C4｜源码中的非法转义序列（SyntaxWarning，未来版本将变 SyntaxError）

`compile()` 实测（Python 3.13，把 `SyntaxWarning` 提升为错误后）：

- `splash.py:34`：`` `<程序目录>\_internal` `` → `invalid escape sequence '\_'`（该模块被 `viewer.py` 导入）
- `gen_assets.py:5`：`F:\conda\envs\fps-screen\python.exe` → `'\c'`；`gen_assets.py:146`：`assets\splash.png` → `'\s'`（compile 只报第一个，实际同文件还有其他处）

影响：每次编译/导入产生告警；若 CI 或用户使用 `-W error`，或未来 Python 版本将其升级为错误，则**导入即刻失败**（`splash.py` 被观看端导入）。修复：文档字符串加 `r` 前缀或把 `\` 写成 `\\`。

### C5｜`HostRuntime._peer_key_at` 只增不减

`host.py:825`（`self._peer_key_at = {}`）与 `1631-1634`（冷却表写入）——`share_id` 由 `_next_share_id` 单调递增且**断开不复用**，因此每出现一个新的共享成员就会留下一条永不清理的记录。属极缓慢的内存增长（每条 ~100 B），长跑数月或"反复开共享"场景下可观测。建议在 `_unregister_sharer` 里 `pop` 对应键，或按时间批量清理。

### C6｜`_hotkey_tid` 竞态：启动期退出会导致热键不注销

`viewer.py:2926-2939`（`_stop_hotkeys`）在 `_hotkey_tid` 为空时直接返回；而 `_hotkey_tid` 在 `_hotkey_loop` 开头（2992 行）才赋值。若 `quit()`/`run()` 的 finally 在热键线程完成注册前执行，`UnregisterHotKey` 不会执行（进程退出时由系统回收，故实际影响小）。建议在注册成功后回填一个"已注册"标志，退出时无论 tid 是否就绪都尝试 `UnregisterHotKey(None, hid)`。

### C7｜监听 backlog 偏小

`host.py:1863 / 1874 / 1881`：三处 `server.listen(5)`。而 `host.net.max_clients` 默认为 32（含握手中）。突发连接（多人同时进入）时内核 accept 队列仅 5，多余连接可能被直接拒绝（对端表现为连接重置）。建议取 `max_clients` 量级（如 `listen(min(128, max_clients * 2))`）。

### C8｜`MSG_VIDEO` 先登记共享者、后校验负载

`host.py:1124-1126`：`if kind == MSG_VIDEO: if info.share_id is None: runtime._register_sharer(sock, info)` 之后的 `try: parse_video(payload)` 才校验结构。一条损坏视频帧即可让该连接**出现在所有观看端的源列表里**并触发一次 roster 广播（随后可能又因超限/断开而消失）——表现为面板源列表抖动。建议先校验通过再登记。

### C9｜死代码、未使用导入与文档漂移

- `host.py:521 _send_ctrl_or_drop`：**在生产路径中无任何调用者**（仅 `tests/test_optimize_stage1.py:599` 引用）。而 `docs/优化方案` 把"B4 控制消息写失败即断开"标注为落地在 `host._send_ctrl_or_drop`——实际生效路径是 `_reply_ctrl` + 调用方返回致命原因。文档与实现漂移，且真正的路径缺少那条"与文档同名"的测试。
- 未使用导入（`pyflakes` 实测）：`host.py:28 struct`、`host.py:37 MSG_CTRL`、`host.py:49-52` 整块 `from screen import (...)`（注释说明是刻意的 re-export 契约，建议加 `# noqa` 或 `__all__` 说明）、`codec.py:30 numpy as np`。
- `viewer.py:2626`：`h = self.root.winfo_height() or ...` 计算后未使用（`_position_top_right` 只用 `w`）。

### C10｜`host_ui` 对 `capture` / `frp` 未做 isinstance 校验

`host_ui.py:181`（`frp = self.runtime.cfg["host"].get("frp", {})`）、`host_ui.py:270`（`cap = ...get("capture", {})`）——`get` 返回非对象时后续 `.get(...)` 抛 `AttributeError`，`HostConsole.__init__` 失败 → `host.main()`（2576-2579）捕获后**静默回退命令行模式**。用户看到的是"双击 exe 没有界面/没有反应"，与 README FAQ 中的症状重叠，但真实原因是配置格式。建议与 `_client_net_cfg` 同口径兜底。

### C11｜发送统计的两处小瑕疵

- `host.py:2263-2264`：`send_fps = (len-1) / (send_window[-1][0] - send_window[0][0])`——两个样本时刻理论上可能相同（极小概率），会抛 `ZeroDivisionError`（被 `_perf_loop` 兜住，但整拍统计丢失）。建议加分母保护。
- `host.py:2189 / 2204`：`now = time.perf_counter()` 在**编码开始前**取得，却作为"编码完成时刻"追加进 `enc_window`，因此 `encode_fps` 反映的是编码**启动**频率而非完成频率（高速编码器下差异小，但语义与注释"记录每次编码完成时刻"不符）。

### C12｜`_upgrade_config` 无改动时不写回版本号

`common.py:621-624`：只在 `changes` 非空时才写 `raw["config_version"] = CONFIG_VERSION`。因此一份"已是安全默认值但 `config_version` 缺失"的旧配置每次启动都会重跑升级判定（幂等、无副作用，但与文档"迁移只发生一次（写回时同时写入 config_version）"的描述不完全一致，且会让每次启动多一次文件校验）。建议无论是否有改动都补写版本号。

### C13｜测试覆盖缺口

- `tests/test_optimize_stage1.py:887`：`test_byte_bucket_throttles_then_refills` 的断言弱于其注释意图（见 A1），**未能覆盖 2 倍补充缺陷**。
- `tests/e2e_multiview.py`、`tests/e2e_signalwin.py`：文件名不匹配 `-p "test*.py"`，长期不在默认回归中（`docs/优化方案` 已登记）。
- `HostRuntime._peer_key_at`、`logger._prune_old`、`FrpManager.stop()` 的失败分支、`CaptureSource.set_params` 的 `cap is None` 分支均无对应用例。
- **新增（A0 相关）**：全仓**没有任何一条**覆盖「frpc 以 `localhost` 回连 → 命中 `::1` → 只绑 IPv4 回环时不可达」的用例；`tests/test_item131_hardening.py` 反而断言了「`0.0.0.0` 会被迁移成 `127.0.0.1`」，把触发 A0 的行为固化成了期望值。

### C14｜共享端没有任何「公网隧道可用性」自检

`host.py` 的 `FrpManager.is_running()` 只回答"frpc 进程在不在"，`print_public_addr()` 只把 `public_addr` 原样播报；`_log_security_notice()` 也只谈监听地址与准入。**整条链路缺少一次"从公网地址回连本机并完成握手"的自检**——而这恰恰是唯一能发现 A0 的手段（项目里已经有现成实现：`viewer._collect_diagnostics()` 对每个频道做 `client_handshake`，`_tmp_honeypot.py` 也做过同类探测）。建议共享端在启动后/点「启动隧道」后异步做一次：`connect(public_addr)` → 发 `FS02` → 等 `OK02`，失败则在 GUI 与日志明确报"公网地址未指向本机监听端口"。

### C15｜观众端把「隧道不可达」报成无法归因的错误

`common.recv_exact` 在"TCP 已建立但对端不发数据即关闭"时抛 `连接提前关闭，收到的数据不完整`；观众端原样写进日志与状态栏。这句话在**隧道／端口映射未指向共享端、frpc 未运行、共享端崩溃**三种完全不同的故障下都会出现，而共享端在这三种情况下**都不会留下日志**，用户只能在两端之间盲猜（本次故障即因此拖延定位）。建议在 `client_handshake` 失败处补一句可操作的提示，例如：「TCP 已连通但未收到服务端握手：通常是内网穿透/端口映射没有指向共享端的监听端口（frpc 日志会写 `连接映射目标 [tcp://localhost:PORT] 失败`），也可能是共享端未启动」。

### C16｜`screen.py` 把 `dxcam.create` 的任何 `TypeError` 都当成"不支持 output_color"，且紧随其后的日志与告警自相矛盾

**位置**：`screen.py:117-135`

```python
try:
    self._camera = dxcam.create(output_idx=..., output_color="BGR")
except TypeError:                      # ← 范围过宽：dxcam 内部（comtypes/winrt 栈）任何 TypeError 都会落到这里
    log.warning("dxcam 不支持 output_color 参数，画面可能红蓝互换，请升级 dxcam")
    self._camera = dxcam.create(output_idx=...)      # ← 不带 output_color 重试，成功后拿到的是 RGB
self._effective = "dxgi"
log.info("采集后端: dxgi（显示器 #%d，BGR）", self.monitor)   # ← 无条件宣称 BGR，与上一行告警冲突
```

**问题**：① `dxcam.create` 内部是一个很深的第三方栈（DXGI/comtypes/winrt），任何位置抛出 `TypeError`（例如参数拼写、库版本不匹配、内部类型错误）都会被误判为"版本不支持 output_color"，并在**去掉 output_color 后重试成功**——重试成功意味着拿到的是默认 RGB 帧，而全链路按 BGR 处理 → **红蓝互换且只留一条 WARNING**；② 紧接的 INFO 日志硬编码 "BGR"，与刚打完的"可能红蓝互换"告警相互矛盾，排障时极易被后一行说服。实测这两行就是相邻出现的（`logs/app_20260822*`～`app_20260911*` 的单测日志中均可见）。

**修复方向**：先探测签名再调用（`inspect.signature(dxcam.create)` 判断是否有 `output_color`），或只在确认是"未知关键字参数"时才回退（`except TypeError as e: if "output_color" not in str(e): raise`）；回退成功后日志应如实写"已回退为 RGB（红蓝可能互换）"，不要再说 BGR。

### C17｜宿主控制台的「启动/停止隧道」在 Tk 主线程内同步阻塞（start ≈1 s、stop 最长 5 s）

**位置**：`host_ui.py:370-382`（`_frp_start` / `_frp_stop` 直接调 `FrpManager.start()/stop()`）

`FrpManager.start()` 会阻塞到"轮询 1 秒确认 frpc 没有秒退"（`host.py:745-755`），`stop()` 会 `proc.wait(timeout=5)`。两者都在 Tk 回调里执行 → **点一下按钮，控制台界面冻结约 1 秒 / 最长 5 秒**（期间日志区、客户端列表、性能区全部停更）。这与项目自己在共享端/观看端反复强调并已修复的"不在主线程做阻塞操作"约定不一致（第 60 条、B7 都把 `join(2.0)` 移出主线程）。

**修复方向**：与 `viewer._panel_toggle_share` 同款处理——放进工作线程，用 `_post_ui` 式回调回主线程更新状态；或把 `start()` 的验活轮询改为异步（启动后注册一个 `after(1000, 复查)`）。

### C18｜宿主控制台的客户端表格仍每 500 ms 全删全建

**位置**：`host_ui.py:551-561`（`_refresh` 里 `tree.delete(*tree.get_children())` 后整表重插）

第 37 条只修掉了"双刷新链"，第 115 条/C4 把**观看端**的两棵树改成了增量刷新（`_panel_refresh_list`/`_panel_refresh_sources` 只更新值变化的行），**共享端这张客户端表没有同步这个改动**：每 500 ms 删光重建 → 行选中丢失、滚动位置被拽回顶部、长期可见闪烁（客户端多时更明显）。

**修复方向**：照搬 `_panel_refresh_list` 的增量写法（行数不变时只 `tree.item(iid, ...)`），或用 `iid=addr` 稳定标识 + 值比较。

### C19｜`_ask_credentials` 在等待 Tk 就绪时还有一段 60 秒的 0.1 s 轮询（补 A3）

**位置**：`viewer.py:818-826`

```python
deadline = time.time() + 60
while time.time() < deadline:
    root = owner.root
    ready = getattr(owner, "_mainloop_ready", None)
    if root is not None and (ready is None or ready.is_set()):

    time.sleep(0.1)          # ← 接收线程在此最长空转 60 秒（同样不受 stop() 影响）
```

6. **A0（实测复现脚本，2 分钟可重跑）**：临时在 `5700` 上分别以「IPv4-only」和「双栈 `::`」各起一个监听，然后从公网侧连 `[隧道域名]:[公网端口]` 并发握手魔数 `FS02`，观察本地是否收到连接：
   ```python
   import socket, threading, time
   def listen(v6):
       s = socket.socket(socket.AF_INET6 if v6 else socket.AF_INET, socket.SOCK_STREAM)
       s.setsockopt(socket.SOL_SOCKET, socket.SO_EXCLUSIVEADDRUSE, 1)
       if v6:
           s.setsockopt(socket.IPPROTO_IPV6, socket.IPV6_V6ONLY, 0); s.bind(("::", 5700))
       else:
           s.bind(("127.0.0.1", 5700))
       s.listen(5); s.settimeout(12)
       try:
           c, a = s.accept(); print("到达！来源", a, "魔数", c.recv(4)); c.sendall(b"OK02"); c.close()
       except socket.timeout:
           print("12 秒内无隧道连接到达")
       finally:
           s.close()
   for v6 in (False, True):
       print("--- %s ---" % ("双栈 ::" if v6 else "IPv4-only 127.0.0.1"))
       threading.Thread(target=listen, args=(v6,), daemon=True).start(); time.sleep(0.8)
       c = socket.create_connection((TUNNEL_HOST, TUNNEL_PORT), timeout=8)  # 隧道域名、公网端口
       c.sendall(b"FS02")
       try: print("公网侧收到", c.recv(16))
       except Exception as e: print("公网侧", type(e).__name__, e)
       c.close(); time.sleep(12)
   ```
   实测结果：**IPv4-only → 无连接到达、公网侧收到 `b''`；双栈 `::` → 本地收到来源 `('::1', …)` 的连接与魔数 `b'FS02'`、公网侧收到 `b'OK02'`**。配合 `C:\ProgramData\SakuraFrpService\logs\` 里 frpc 的 `连接映射目标 [tcp://localhost:5700] 失败 … 连接被拒绝`，即可完整闭环证明 A0。

## 8. 本次定位用到的排查路径（可复用）

若再遇到"公网连不上 / 隧道没画面"，按下列顺序取证，通常 3 步内可定位（本次即由此定位到 A0）：

1. **观众端日志**（`logs\app_*.log` 或 `%LOCALAPPDATA%\TeamVision\logs\`）：看失败发生在哪一步——`WinError 10061`（对端拒绝，隧道或服务未起）、`连接提前关闭，收到的数据不完整`（**TCP 通了但握手无回应**，指向隧道→本机这一段）、`非法的消息类型`（流错位/版本不匹配）。
2. **共享端日志**：如果观众端报的是"握手无回应"，而**共享端完全没有任何接入记录**，即可断定**连接根本没有到达共享端进程**（问题在隧道/端口映射，不在程序内部）。
3. **第三方隧道自己的日志**（樱花：`C:\ProgramData\SakuraFrpService\logs\SakuraFrpService.YYYYMMDD.log`）：里面会直接写出「使用 >>域名:远端端口<< 连接你的隧道」与「连接映射目标 [tcp://**本地地址**:本地端口] 失败 … 连接被拒绝」——**这一步能直接看到隧道实际回连的地址是 `localhost` 还是 `127.0.0.1`，是判定 A0 的关键证据**。
4. **进程与端口**：`tasklist | grep -i "frp\|sakura"`（谁在跑 frpc、是否以服务/SYSTEM 身份）、`netstat -ano | grep :<本地端口>`（共享端是否在监听、绑的是 v4 还是 v6）。
5. **端到端探针**：本地临时监听目标端口（如 `127.0.0.1:5700`），再从公网侧连隧道地址并发送握手魔数 `FS02`——能收到 `FS02` 就说明隧道确实打到了本进程；收不到即证明映射/回连地址不匹配。**注意分别用「IPv4-only」与「双栈 ::」各测一次**，即可直接区出 A0 这类地址族问题。
