## 2. 硬性判定标准（不满足即不写进报告）

一条发现要成立，必须同时给出：

1. **精确位置**：`文件:行号` + 关键代码原文（1~5 行）。
2. **触发条件**：什么输入/时序/配置会走到它（不是"可能有问题"，是"会怎样"）。
3. **后果**：用户可见或进程级后果（黑屏 / 卡死 / 永久失效 / 内存无上限 / 崩溃 / 假状态）。
4. **证据**：满足任一即可 ——
   - 最小复现脚本（放 `_tmp_audit_<域>*.py`，本仓库 `.gitignore` 已忽略 `_tmp_*.py`）实跑输出的关键几行；
   - 或明确到行的静态推演链（"第 N 行返回 X → 第 M 行按 X 分支 → 第 K 行不复位"）；
   - 或"把该处改回缺陷形态会让哪个既有用例翻红 / 现有用例为何钉不住它"。
5. **同族入口**：`grep` 出的其它调用点，逐条标注"同缺陷 / 已正确 / 不适用及原因"。
6. **去重声明**：说明与既有 audit 条目的关系（新问题 / 既有条目的未收口残留 / 已登记条目重复）。

## 3. 不要写进报告的东西

- 风格、命名、注释措辞、行长、import 顺序 —— ruff/mypy 已覆盖或本仓库已明确豁免。
- "建议重构 / 建议抽函数 / 建议加类型注解" —— 没有具体缺陷的边界提议。
- 无法给出触发路径的"潜在风险"。
- 已登记条目的复述。
- 臆测的第三方行为。不确定的事实要么实测要么标注"未验证"并说明验证方法。

**宁可只报 2 条站得住的，不要报 20 条凑数的。**
